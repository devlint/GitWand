# v3.11.1 History-aware LLM fallback: design

**Date:** 2026-09-24
**Roadmap:** `ROADMAP.md` § "v3.11.1 — History-aware LLM fallback"
**Out of scope:** the MCP prompt paths (`buildResolveHunkPrompt`, `gitwand_resolve_hunk_llm`), rename following, and a dedicated Rust command. See §9.

---

## 1. What exists today

The code has three separate LLM prompt builders, and none of them share code:

| Path | Builder | Produces `llm_proposed`? |
|---|---|---|
| Core fallback (desktop + CLI via `resolveAsync`) | `buildPrompt`, `packages/core/src/resolvers/llm-fallback.ts:89-134` | yes |
| Desktop "Resolve with AI" / "Resolve All with AI" | `useAIProvider.buildUserPrompt`, `apps/desktop/src/composables/useAIProvider.ts:164-184` | no, the suggestions are staged |
| MCP | `buildResolveHunkPrompt`, `packages/mcp/src/tools/resolve_hunk.ts:89-138` | no |

None of them sends blame, history, commit messages or the merge base, and none has a token budget. The only bound is `contextLines`, which counts lines.

Four facts shape the design:

- **Core does no I/O.** It calls an injected `LlmEndpoint.call(prompt)` (`types.ts:140-163`). History must reach core through the same kind of injection.
- **Blaming the conflicted working tree is useless.** Every line of the hunk comes back as "Not Committed Yet". Useful history needs revision-scoped queries, and no existing Tauri command accepts a revision.
- **The theirs-side SHA is available but dropped.** `git_repo_state` returns `operation_head` (`MERGE_HEAD`, `REBASE_HEAD`, `CHERRY_PICK_HEAD` or `REVERT_HEAD`). `useGitWand.ts:642-663` discards it when building `MergeContext`, which carries ref names only (`types.ts:518-532`).
- **`ConflictContext` already has `ourCommitMessage` / `theirCommitMessage` slots** (`useAIProvider.ts:85-100`), but nothing fills them.

## 2. Scope

**In scope.** Give the two desktop-reachable paths (the core `llm_proposed` fallback, and "Resolve with AI" / "Resolve All with AI") one shared history context. For each side, it lists the commits that changed the conflicting lines since the merge base, with their messages, and adds the range-limited diffs when the budget allows. The context has an on/off switch and a token budget. When history cannot help, the prompt says so explicitly. The outcome is recorded in `LlmTrace`.

**Not in scope.** See §9.

This revises one line of the #196 spec (`2026-09-17-ai-hunk-queue-design.md:29`, "Any change to prompt content … out of scope"). That exclusion was scoped to #196, and this feature deliberately changes the content of the "Resolve with AI" prompt.

## 3. Decisions

| Question | Decision |
|---|---|
| Which paths | `llm_proposed` + desktop "Resolve with AI". The MCP is left unchanged. |
| What history | **Intent first**: per side, the commits that touched the lines since the merge base (short SHA, author, date, subject, body). The **range-limited diff** is added only while the budget allows. Nothing before the merge base. |
| Activation | On by default. `history.enabled` + `history.budgetTokens` (default 1500) in both `.gitwandrc` and the app Settings. |
| When history is useless | Omit it, **and say so in the prompt** with one line giving the reason. Also record it in `LlmTrace`. Timeout of 2 s per file. Pure moves are filtered out. |
| Architecture | The algorithm lives in core. Git execution is injected as `runGit`. There is no new Tauri command. |

## 4. Architecture

```
packages/core/src/history/
  types.ts        HunkHistory, SideHistory, HistoryCommit, GitRunner
  locate.ts       locateBlock(sideFileLines, blockLines, estimatedLine) -> {start,end} | null
  collect.ts      collectHunkHistory(runGit, input, cache) -> Promise<HunkHistory>
  parse.ts        parseLogL(stdout) -> HistoryCommit[]      (pure)
  render.ts       renderHistorySection(history, budgetTokens) -> {text, stats}   (pure)
  index.ts
```

```ts
type GitRunner = (args: string[]) => Promise<{ stdout: string; exitCode: number }>;
```

Core only builds argument arrays and parses stdout. It never spawns a process. This keeps the "zero Node.js in core" rule. The hosts provide the runner:

- **Desktop:** `(args) => gitExec(cwd, args)` (`backend.ts:2375`). It already uses discrete args, and it runs under Tauri and under `dev-server.mjs` (`/api/git-exec`). The same TS code runs in both, so Tauri/dev-server parity holds with no extra work.
- **CLI:** `execFile("git", args, { cwd })`, in `packages/cli`.

### 4.1 Identifying the sides

`MergeContext` gains `oursSha?: string` and `theirsSha?: string`.

- `oursSha` is `HEAD`. `theirsSha` is the operation head (`MERGE_HEAD` / `REBASE_HEAD` / `CHERRY_PICK_HEAD` / `REVERT_HEAD`).
- **Desktop:** map `RepoOperationState.operation_head` into `theirsSha` instead of dropping it, and resolve `HEAD` with `rev-parse`.
- **CLI:** `detectMergeContext()` (`packages/cli/src/git.ts:74-116`) adds `rev-parse HEAD` and `rev-parse <operation head>`.
- If either SHA is missing, both sides are `unavailable` with reason `no-sha`.

**Commit ranges per operation.** For merge and rebase, each side is `<mergeBase>..<sideSha>`, where `mergeBase` is `git merge-base <oursSha> <theirsSha>`. For cherry-pick and revert, git merges against the parent of the applied commit, not the fork point. The theirs side is therefore `<theirsSha>~1..<theirsSha>`, which is exactly the one commit being applied (or reverted). The ours side stays `<mergeBase>..<oursSha>`. `HistoryRefs` carries the `operation` for this reason.

The merge base comes from `git merge-base <oursSha> <theirsSha>`. It is computed once per file and cached for the whole `resolveAsync` / queue run. An empty result gives reason `no-merge-base`.

### 4.2 Locating the lines on each side

Line numbers in the conflicted file do not match `HEAD`, because auto-merged regions shift them. So:

1. Read `git show :2:<path>` (ours) and `git show :3:<path>` (theirs). They are cached per file.
2. `locateBlock` searches each side file for the hunk's exact `oursLines` / `theirsLines` block. When the block appears more than once, it picks the match closest to `hunk.startLine` (the opening-marker line; auto-merged regions shift it by a few lines at most, which only matters as a tie-breaker). If there is no match, the side is `unavailable` with reason `locate-failed`.
3. If a side is empty (it removed the block), or its stage file does not exist (modify/delete: it deleted the file), the reason is `side-deleted` and we fall back to file-level history: `git log <base>..<sideSha> --no-merges -n 3 --format=<fmt> -- <path>`, with no diffs. That log contains the commit that removed the code, which is exactly the intent the model needs.
4. add/add needs no special case: both stage files exist, and `-L` walks back to the commit that created the file.

### 4.3 One query per side

```
git log --no-color -L <a>,<b>:<path> <range> --no-merges -n 5 --format=<fmt>
```

`--no-color` is there because a user config with `color.ui=always` would otherwise put escape codes in the output.

`<fmt>` separates the fields with unit and record separator markers: `%x1e%H%x1f%an%x1f%as%x1f%s%x1f%b%x1f`. `-L` prints each commit's patch limited to the range right after it. That patch is the `rangeDiff` fallback, so a single call gives both the intent and the diff.

**Pure-move filter.** If a commit's range patch removes and adds exactly the same multiset of lines (ignoring leading and trailing whitespace), the commit is a move with no semantic change. It is dropped.

**Cost per hunk sent to the LLM:** 2 `log -L`. **Per file:** 1 `merge-base`, 2 `show`, all cached. **Per run:** 1 `rev-parse HEAD`. Each `collectHunkHistory` call has a 2 s budget (`Promise.race`), and the cached per-file queries count against the budget of the first hunk that triggers them. The budget is per hunk, not per file: in "Resolve All with AI", the hunks of one file are collected minutes apart, between model calls, so a per-file deadline would already have expired by the second hunk. On timeout, the sides not yet collected get reason `timeout`. The git process itself is not killed; see §9.

### 4.4 Types

```ts
interface HistoryCommit {
  sha: string;        // full; rendered short
  author: string;
  date: string;       // YYYY-MM-DD
  subject: string;
  body: string;
  rangeDiff: string;  // "" when file-level fallback
}
type HistoryUnavailableReason =
  | "no-sha" | "no-merge-base" | "side-deleted" | "locate-failed" | "no-commits" | "timeout" | "git-error";
interface SideHistory {
  status: "ok" | "unavailable";
  reason?: HistoryUnavailableReason;
  commits: HistoryCommit[];
}
interface HunkHistory {
  mergeBase: string | null;
  ours: SideHistory;
  theirs: SideHistory;
}
```

`side-deleted` has `status: "ok"` when the file-level fallback found commits, and `"unavailable"` when it found none. Either way, the rendered text states that the side removed the block. When `-L` finds no commit after the pure-move filter, the side is `unavailable` with reason `no-commits`.

`collectHunkHistory` **never throws**. Any failure (non-zero exit, unparsable output, timeout, runner rejection) becomes `unavailable` with a reason.

## 5. Rendering and budget

`renderHistorySection(history, budgetTokens)` is pure and estimates tokens at `ceil(chars / 4)`. There is no tokenizer in the repo, and we do not add one.

```
## Why each side changed these lines (since merge-base abc1234):
### ours (HEAD)
- def5678 2026-09-10 Alice: Extract retry policy
  <body>
  <rangeDiff>
### theirs (MERGE_HEAD)
History unavailable: no commit since the merge base.
```

**Truncation order** when over budget. Each step is applied until the text fits:

1. Drop the `rangeDiff`s from oldest to newest. The newest commit's diff on each side goes last.
2. Drop the bodies, from oldest to newest.
3. Drop whole commits, oldest first.

**Invariant:** the newest commit's short SHA + subject on each `ok` side is never dropped. Neither is any `unavailable` line. If these alone exceed the budget, they are still sent (a few dozen tokens at most) and the stats are marked `truncated`.

`stats = { status: "included" | "truncated" | "unavailable" | "disabled", reasons: HistoryUnavailableReason[], commitCount, estTokens }`. `unavailable` means that neither side is `ok`.

## 6. Integration

### 6.1 Core `llm_proposed` path

- `GitWandOptions` gains `gitRunner?: GitRunner`. `LlmFallbackConfig` gains `history?: { enabled: boolean; budgetTokens: number }` (default `{ enabled: true, budgetTokens: 1500 }`).
- `runLlmFallbackPhase` (`resolver/llm-pipeline.ts`) calls `collectHunkHistory` **only for the hunks it is about to send**. Hunks resolved deterministically cost no git calls. With no `gitRunner`, or with `history.enabled: false`, the stats are `disabled` and the prompt is the same as today.
- `buildPrompt` takes the rendered section and inserts it between "Context" and "Conflict hunk to resolve".
- `LlmTrace` gains `history: HistoryStats`. `promptHash` changes when history is included, which is expected.
- **Desktop worker boundary:** the runner crosses into the Web Worker as a `Comlink.proxy`, exactly like the endpoint (`useGitWand.ts:682-690`, `utils/coreEngine.ts`).

### 6.2 Desktop "Resolve with AI"

- `ConflictContext` gains `history?: string`, the already-rendered section. `ourCommitMessage` / `theirCommitMessage` are **removed**, because the section replaces them. `buildUserPrompt` inserts the section before the hunk.
- `useAiHunkQueue.run` calls `collectHunkHistory` from `@gitwand/core` on the main thread, with a `gitExec` runner and a cache shared across the run. It then renders the section and passes it to `suggest()`. This covers the per-hunk button and "Resolve All with AI" alike.

### 6.3 Trace UI

`LlmTracePanel.vue` shows one line built from `history` stats, for example "History: 4 commits (≈900 tokens), truncated" or "History: unavailable (no merge base)". It is localized.

## 7. Settings

- **`.gitwandrc`:** `llmFallback.history: { enabled?: boolean, budgetTokens?: number }`, parsed by `parseLlmFallbackFromRc` (`useGitWand.ts:125-151`) and by the CLI's `resolveLlmConfig`. `budgetTokens` is clamped to 200–8000.
- **Desktop Settings:** `aiHistoryEnabled: boolean` (default `true`) and `aiHistoryBudgetTokens: number` (default `1500`), added to **both** `useSettings.ts` (`AppSettings`) and `SettingsPanel.vue` (`Settings`). The labels and help text go in all 5 locales. The help text states that commit messages and diffs are sent to the configured AI provider.
- **Precedence.** When `.gitwandrc` sets `history.enabled: false`, it wins on both desktop paths, so a repository can forbid sending its history to an LLM. Otherwise the app Settings apply. A `budgetTokens` value in `.gitwandrc` also overrides the app value. The CLI uses `.gitwandrc` only.

## 8. Testing

**Core, with real temporary git repos** (tests may use `child_process`; the shipped code does not):

- merge, rebase and cherry-pick conflicts: the right commits end up on each side, and nothing from before the merge base;
- add/add → both sides collected normally, down to the commit that created the file; modify/delete and a side that removed the block → `side-deleted` with the file-level fallback;
- unrelated histories → `no-merge-base`;
- a block moved by one commit and edited by another → the move is filtered and the edit is kept;
- a block duplicated in the file → `locateBlock` picks the nearest match; a block absent from the stage file → `locate-failed`;
- a runner that never resolves → `timeout` inside the budget, and resolution continues;
- a runner that rejects / exits non-zero → `git-error`, and no throw.

**Core, pure:**

- `parseLogL` on captured `-L` output, including bodies with blank lines and a patch-free file-level log;
- `renderHistorySection`: the truncation order, the newest-subject invariant, the `unavailable` lines, and the stats;
- **the first assertion on prompt content** in `buildPrompt`, both with and without history. Today only the hash is tested (`llm-proposed.test.ts:210,324`).

**Desktop:**

- `useAiHunkQueue` passes `history` when it is enabled and omits it when it is disabled or overridden by `.gitwandrc`;
- `LlmTracePanel` renders the history line;
- `useGitWand` maps `operation_head` into `theirsSha`.

**CLI:** the `execFile` runner, and `.gitwandrc` `history` parsing and clamping.

There is no new Tauri command, so there is no `commandRegistry.ts` entry and no parity probe case. `gitExec` is already registered. The LLM pipeline is not a benchmarked hot path, so there is no bench change.
