# v3.11.0 Merge preview-to-apply: design

**Date:** 2026-09-12
**Scope:** the resolution-loop half of `ROADMAP.md` v3.11.0. The other 7 lots (libgit2
stage/unstage, libgit2 blame re-enable, dev-server route drift audit, Linux inotify validation,
forge-side auto-merge, Finder-like folder navigation, history-aware LLM fallback) are out of scope
and get a second planning pass.
**Implementation plan:** `2026-09-12-v3.11.0-preview-to-apply-plan.md`

---

## 1. Problem

The Conflict Predictor (v2.20.0) tells the user what *would* happen and then abandons them. They
merge blind or detour through a scratch worktree. Worse, the engine computes a complete resolution
during the preview and throws it away: `useMergePreview.ts:155-165` keeps three scalars per hunk
and discards `mergedContent`, `resolvedLines` and `confidence`.

Two threads close the loop:

- **Half 1, the apply pipeline.** Apply from preview, hunk-level opt-out, confidence threshold.
- **Half 2, the CodeMirror thread.** MergeEditor textarea to CodeMirror 6, editable diff, and the
  #128 split-affordance follow-up.

The threads touch disjoint files and can be built in parallel.

## 2. Baseline, as audited

Every claim below was verified against the tree at `3.10.1`.

### 2.1 The preview is a simulation, not a merge

`preview_merge` / `preview_rebase` / `preview_cherry_pick` (`src-tauri/src/commands/read.rs:1510`,
`:1710`, `:1823`) run `git merge-base`, then `git show <rev>:<path>` for the three versions into
temp files, then `git merge-file -p --diff3`. Nothing touches the index or the worktree.

The only returned type carries four fields (`src-tauri/src/types.rs:655-663`):

```rust
pub struct FileMergePreview {
    pub file_path: String,
    pub conflict_content: String,
    pub has_conflicts: bool,
    pub is_add_delete: bool,
}
```

No hunks, no confidence, no blobs, no SHAs. **Any apply must run the real operation and recompute.**

Three defects in the current implementation:

| Defect | Location | Consequence |
|---|---|---|
| Fixed temp-file names in the shared temp dir | `read.rs:1892-1895` | Two concurrent previews on the same file race. Live today: the panel re-runs previews on operation switch |
| `git merge-file` called without `-L` labels | `read.rs:1919` | Absolute temp paths leak into the conflict markers the user reads |
| Rebase dedup discards commit provenance | `read.rs:1773-1804` | Cannot tell which replayed commit produced a conflict |

### 2.2 The engine's output is computed and discarded

`useMergePreview.ts:139` calls `core.resolve(raw.conflict_content, raw.file_path)` with **no options
object**, so it runs on engine defaults (`prefer-theirs`, `minConfidence: "high"`) and ignores the
repo's `.gitwandrc` entirely. It calls `resolve`, not `resolveAsync`, so there is no tree-sitter
structural pass and no LLM fallback.

The real apply path (`useGitWand.loadRealFiles`) uses `resolveAsync` with policy and `MergeContext`.
**The preview therefore reports a lower bound.**

### 2.3 No numeric confidence threshold exists

Both gates compare `Confidence` *labels* through `CONFIDENCE_ORDER` (`resolver/policy.ts:56-61`):

- `resolver/index.ts:238-244`, the format-aware path
- `resolver/index.ts:261-267`, the main textual path

The 0-100 score exists (`ConfidenceScore`, `types.ts:71-120`; formula `scoreFromDimensions`,
`patterns/utils.ts:55-75`) but nothing anywhere compares it.

**Footgun:** `complex` scores **60 / "medium"**, not 0 (`patterns/complex.ts:14-19`,
`makeScore(100, 100, 0)`). What actually keeps `complex`, `token_level_merge`, `generated_file` and
`llm_proposed` unapplied is `assembleResolution()` returning `{lines: null}`
(`resolver/assemble.ts:215-281`), not a low score.

### 2.4 A live bug in the reject affordance

`ResolutionPreviewPanel`'s reject is purely visual. `rejectedPreviewHunks` (`MergeEditor.vue:389`)
is consulted by neither `autoResolutionsSummary` (`:432-436`) nor the "Resolve auto" path, which
runs `resolveFile` and then `buildPartialContent` (`useGitWand.ts:912-945`), re-applying **every**
`autoResolved` hunk. A hunk the user rejected is applied anyway.

Contrast `rejectedLlmHunks` (`:250`), which does feed `canResolve` (`:262-264`).

### 2.5 No dev-server parity for any preview command

`dev-server.mjs` has no `/api/preview-merge`, `/api/preview-rebase` or `/api/preview-cherry-pick`.
`backend.ts:2573-2595` POSTs to a route that does not exist, catches, and returns `[]`;
`previewRebase` (`:2603`) and `previewCherryPick` (`:2618`) are Tauri-only stubs returning `[]`.

Under `pnpm dev:web`, the project's manual-QA method, **the predictor silently reports every merge
as conflict-free.**

### 2.6 CodeMirror is installed but not reusable

The whole editor is inlined in `FileExplorerPanel.vue:117-395`. There is no `CodeEditor.vue` and no
`useCodeMirror.ts`. There is **no test for the component at all**. `oneDark` is applied
unconditionally regardless of the app theme, acknowledged in a comment at `:818-822`.

Worth stating precisely, because it changes the migration risk: the file has a single
`<script setup>` block, so `docStates`, the compartments and the blame models compile into
`setup()` and are already **per-instance**. They behave as singletons only because the panel mounts
once. The extraction is "hoist a per-instance closure into a per-instance factory", which is
mechanical, not a de-globalization.

### 2.7 Bundle headroom is far tighter than documented

Measured on `dist/` exactly the way `perf/bundle-check.mjs` counts:

| | measured | budget | headroom |
|---|---|---|---|
| total | **4744 KB** | 5000 | **256 KB** |
| main (`index-DJWRiNVP.js`) | **882 KB** | 900 | **18 KB** |
| largest other (xterm) | 322 KB | 500 | 178 KB |

The comment at `bundle-check.mjs:88-90` still claims "measured 4287 KB ... ~700 KB of headroom,
enough for a locale addition or a CodeMirror language pack". That was August 2026.

CodeMirror is already perfectly chunk-split (`@codemirror/view` 197 KB, `@codemirror/language`
71 KB, `@codemirror/state` 48 KB, `codemirror` 31 KB, `@codemirror/commands` 28 KB, plus ~90
per-language chunks), so N dynamic importers of the same specifier yield **one** chunk with N
importers. The marginal cost of this whole thread is the new source files.

**The trap:** `SplitCommitModal.vue:20` statically imports `DiffViewer`, so they share a chunk. A
static `CodeEditor` import inside `DiffViewer` would put ~400 KB of CodeMirror into a modal that can
never edit anything, tripping `any_chunk_max_kb: 500`.

### 2.8 Precedents to reuse rather than reinvent

- `App.vue:2525-2563` (`onRebaseBannerAutoResolve`) already implements "run operation, open
  conflicts, `resolveAll()`, `saveAllFiles()`, `stageFiles()`, continue, stop on residual", bounded
  at 100 iterations.
- `useInteractiveRebase.ts:60-112` keeps `pendingSplits` module-level *specifically* so the app
  shell can observe it, with exported free functions.
- `DiffViewer.vue:724-742` is a working full-width `colspan` escape row, with its CSS trap already
  documented at `:716-723`.
- `dev-server.mjs:1225-1257` (`/api/reconstruct-conflict`) is the route shape to copy, and it
  already passes `-L ours -L base -L theirs`.

## 3. Half 1: the apply pipeline

### 3.1 Apply runs the real operation. Always.

Writing the simulated `git merge-file` output into the worktree is unsound, not a trade-off: it
bypasses the index (no stage 1/2/3 entries), leaves no `MERGE_HEAD`, produces wrong content for
renames, submodules, binaries and `.gitattributes` merge drivers, and makes `--continue`
impossible.

New composable `apps/desktop/src/composables/useApplyFromPreview.ts`, taking an **explicit deps
object** rather than calling `useGitWand()` itself (App.vue owns the single instance), so it is
unit-testable with fakes:

```
0. pre-flight   gitRepoState(cwd).state === "clean", else refuse before any mutation
1. snapshot     useSnapshots().capture(cwd, "resolution", `Apply from preview: ${op} ${ref}`)
2. run real op  merge  -> useGitRepo.mergeBranch(ref, noFf)
                cherry -> useGitRepo.cherryPick([sha])
                rebase -> gitRebaseOnto(cwd, ref)          [new command]
3. refresh      repoRefresh() + refreshRepoState()
4. clean?       -> finalize, report, done
5. conflicts:   mergeOpenPath(cwd) -> resolveAll({ shouldApply }) -> saveAllFiles()
                -> stageFiles(fullyResolvedPaths) -> repoRefresh()
6. residual 0?  -> finalize (merge / cherry-pick / rebase --continue)
   residual >0? -> STOP, select residualFiles[0], show report. Never auto-continue.
7. rebase only: loop 5-6, bounded at 100 (precedent App.vue:2528-2562)
```

Step 7's loop is **required** for rebase, not an optimization: `preview_rebase` dedups per file
across replayed commits, so a multi-commit rebase surfaces conflicts step by step and a single pass
resolves only the first step.

**Reused unchanged:** `useGitRepo.mergeBranch` (`:1099`), `cherryPick` (`:1173`), `mergeContinue`
(`:1156`), `abortMerge` (`:1143`), `gitCherryPickAbort` / `gitCherryPickContinue`,
`gitRebaseAction`, `stageFiles` (`:819`), `useGitWand.openPath`, `saveAllFiles` (`:1219`),
`useSnapshots().capture`, App.vue's `advanceToNextConflictOrFinalize` (`:790`).

The emit chain mirrors the existing `mergeBranch` one: `MergePreviewPanel` to `BranchSelector` to
`AppHeader` to `App.vue`.

**Exactly one new Rust command in the release:** `git_rebase_onto(cwd, onto)`. Verified absent:
`ops.rs` has `git_pull`, `git_rebase_action` and `git_interactive_rebase`, but no plain
`git rebase <onto>`. Everything else composes existing commands, because the orchestration
interleaves real git with the TypeScript engine and the engine is frontend-only.

### 3.2 The button's N is an estimate, and the UI says so

Preview and apply cannot agree by construction. The causes, each a real mechanism, get named in a
code comment and in the drift message:

| Cause | Direction |
|---|---|
| Preview uses `core.resolve`; apply uses `resolveAsync` with tree-sitter and policy | preview **under**-estimates |
| `git_changed_files` (`git/cmd.rs:478-495`) is `diff --name-only` with no `-M`, so renames read as add+delete | file set differs |
| `merge-file --diff3` on three blobs vs `ort` with a virtual merge base on criss-cross histories | both |
| `.gitattributes` merge drivers, `merge=union`, binaries, submodules: invisible to the preview | preview **over**-estimates |
| The worktree can change between preview and apply | both |

Only the first is fixable, and it is the largest. Switch the preview to `resolveAsync` with the same
options `useGitWand.loadRealFiles` builds (`:500-503`, `:565-586`), **minus `llmFallback`**: a
preview must never spend money or seconds on a model. That remaining gap becomes one named,
documented source of under-estimation.

Cost: a tree-sitter grammar load on first preview. The preview is behind an explicit click and
grammars are fetched once per session. Acceptable.

**UI contract.** Button label "Merge and auto-resolve", sub-line "Estimated {0} of {1} hunks
auto-resolvable". The word *estimated* is load-bearing.

A new `MergeApplyReport.vue` (extracted, because `MergePreviewPanel.vue` is already 604 lines)
renders a typed outcome:

```ts
interface ApplyOutcome {
  operation: PreviewOperation;
  ref: string;
  estimatedHunks: number;
  snapshotId: string | null;      // null on a repo with no HEAD: say so
  operationError: string | null;
  appliedHunks: number;           // actual
  filesResolved: string[];
  residualFiles: string[];
  residualHunks: number;
  finalized: boolean;
  stoppedReason: "clean" | "residual" | "op-failed" | "resolve-failed" | "loop-bound";
}
```

When `estimatedHunks !== appliedHunks + residualHunks`, render the drift explanation.

### 3.3 Failure semantics: stop, never auto-abort

**Snapshot before the operation, in the orchestrator.** `saveFile` (`useGitWand.ts:1192-1201`)
captures none by design, and `saveAllFiles`'s (`:1231-1235`) comes too late to cover "the merge
itself went somewhere I did not want". Two snapshots per apply is cheap and correct.

Use the existing `kind: "resolution"`. Do **not** add a `SnapshotMeta["kind"]` variant: it is a
serialized union mirrored in Rust, so a new value means Rust plus dev-server plus parity
normalization for zero user benefit. The operation goes in the label.

| Failure | Behaviour |
|---|---|
| Pre-flight fails (op in progress, dirty tree) | Refuse before the snapshot. Git's own message in `repoError`. No state change |
| Operation fails outright | Stop, `operationError` set, nothing resolved. **No abort**: git started none |
| Operation conflicts | Expected, continue to step 5 |
| Resolve or save throws mid-way | Stop. Operation **stays in progress**. Report saved vs unsaved. **Never auto-abort**: that discards the user's partial resolution. Offer `Abort <op>` and `Restore snapshot` as buttons |
| Partially applied | As above, `stoppedReason: "residual"`, land in the merge editor on `residualFiles[0]`, `--continue` not run |
| Rebase loop hits 100 | `stoppedReason: "loop-bound"` |

**Gotcha:** `useGitRepo.stageFiles` (`:819-827`) swallows errors into `error.value` and never
throws. Verify success by re-reading `repoStatus.value.conflicted`, not by absence of an exception.

Abort is offered, never taken automatically. It is the one place where an apply feature can destroy
work irreversibly, and the snapshot covers the worktree but not the user's mental model of which
hunks they had already reviewed.

### 3.4 The numeric threshold is strictly additive

```ts
// packages/core/src/types.ts, next to minConfidence at :553
/**
 * v3.11 additional NUMERIC confidence bar, 0-100, ANDed with `minConfidence`.
 * null or absent means off. Never relaxes the label gate: a hunk must pass BOTH.
 */
minConfidenceScore?: number | null;
```

A distinct name rather than an overload of `minConfidence`: the label option is a public contract
across CLI, MCP and `.gitwandrc`, and a numeric `minConfidence` already exists under `commitReview`
(`config.ts:367`) for an unrelated concept. Two names cost less than one polymorphic one.

`DEFAULT_OPTIONS` (`policy.ts:27-53`) is `Required<GitWandOptions>`, so the type is `number | null`
with a `null` default, following the `mergeContext: null` precedent at `policy.ts:40`.

One shared helper in `resolver/policy.ts`:

```ts
export function normalizeMinScore(v: number | null | undefined): number | null;

export type ConfidenceGateResult =
  | { passed: true }
  | { passed: false; failedOn: "label"; required: Confidence }
  | { passed: false; failedOn: "score"; required: number };

export function checkConfidenceGate(
  confidence: ConfidenceScore,
  minLabel: Confidence,
  minScore: number | null,
): ConfidenceGateResult;
```

Both gate sites (`resolver/index.ts:238-244` and `:261-267`) replace their inline comparison with
this call and build their existing reason strings from the result, plus a new score branch:

> `Confidence score 74 (label: high) is below the 90 required by the caller's minConfidenceScore.`

**This is what defuses the `complex`-at-60 footgun structurally.** The numeric bar can only
*subtract* from the applied set. Setting it to 10 changes nothing, because the label gate and
`assembleResolution`'s `{lines: null}` for the four never-apply types are untouched. There is no
reachable configuration in which a lower numeric bar applies *more*.

**Do not use `TIER_BY_TYPE` for the gate.** `stats/tiers.ts` is documented as a derived metric that
is "NOT a change to resolution logic", and its `token_level_merge: "advancedDeterministic"` means
"does not need the model", not "safe to apply". Wiring it into an apply gate overloads it so a
future metric tweak would silently change resolution behaviour, which is the exact coupling the
file's own comment warns against. It is the right tool for the **UI** (explaining what kind of
residual is left) and stays there.

**Do not export `resolveHunk`.** It takes `Required<GitWandOptions>` plus a `genInfo` blob and sits
*inside* the orchestration that provides the v3.9 guarantees: the file-frequency penalty,
`reclassifyIfGenerated`, the invariant-violation retraction, and `resolveAsync`'s parse-tree
retraction. Exporting it invites callers to reimplement that badly.

Export a narrower **pure query** instead, in a new `packages/core/src/stats/threshold.ts`:

```ts
export function wouldApplyAtThreshold(r: HunkResolution, minScore: number): boolean;
export function summarizeAtThreshold(
  result: MergeResult, minScore: number,
): { applied: number; heldByThreshold: number; manual: number };
```

Everything it needs is already in an existing `MergeResult`, so it answers "would this hunk apply at
threshold X" with **zero re-runs** of `resolve()`, which is what makes an interactive control
viable. It agrees with the engine gate *by construction*, precisely because the gate is additive:
`engine applies at X` is equivalent to `engine applies at 0` **and** `score >= X`.

**The desktop uses the query; CLI and MCP use the option.** The desktop deliberately does not pass
`minConfidenceScore` into the worker, which would force a re-resolve per control tick and
double-filter. A core test pins their agreement.

**Audit trail:** no new structure. The decline reason lands in `HunkResolution.resolutionReason`,
already the audit surface for every other decline (the existing label gate adds no `TraceStep`
either) and already what the UI renders. `DecisionTrace` stays a record of *classification*, not of
caller policy; mixing caller options in would make traces non-reproducible from the hunk alone.

### 3.5 Per-hunk opt-out belongs in the merge editor, not the preview panel

A preview hunk index is a simulation artefact and will not match the real merge's indices, so a
tick-box in the preview cannot bind to anything. The *threshold* transfers soundly because it is
index-independent.

So: **the preview gets the threshold, the merge editor gets the checkboxes.** That is also exactly
where the live bug of section 2.4 lives, so the two goals collapse into one piece of work instead of
two.

New module-level singleton `apps/desktop/src/composables/useResolutionSelection.ts`, documented like
`useSnapshots` ("one repo active at a time; every consumer must see the same set"):

```ts
minScore: Ref<number>                      // 0 means off
excludedByFile: Ref<Map<string, { contentStamp: string; indices: Set<number> }>>
shouldApply(filePath, index, resolution): boolean
toggle(filePath, index, contentStamp): void
remapAfterApply(filePath, appliedIndices: number[], newContentStamp: string): void
resetFile(filePath): void
resetAll(): void
```

Key: `` `${filePath}#${hunkIndex}` ``. The positional conflict-block index is the currency every
existing apply primitive already speaks (`buildPartialContent`, `replaceConflictByIndex`,
`resolveHunkCustom`, `rejectedPreviewHunks`). Do not invent hunk ids.

**Exclusion is desktop state, not a core option.** Core's question is "what *can* be resolved";
"what the user chose not to apply" is UI state with no stable identity across re-resolves. Contrast
`wouldApplyAtThreshold`, which is a pure function of the engine's own output and therefore belongs
in core.

Threading keeps `useGitWand` a pure function of its arguments, so its existing tests do not change
shape:

```ts
buildPartialContent(original, resolutions, shouldApply?)   // default preserves today's behaviour
resolveFile(path, opts?: { shouldApply })
resolveAll(opts?: { shouldApply })
```

App.vue reads the singleton and passes the predicate, since it already owns both sides.

**The subtle bug to catch in review:** `resolveAll` (`:844-851`) and `resolveFile` (`:899`)
short-circuit on `file.result.mergedContent`, which already contains *every* resolution. That fast
path must be **skipped whenever a filter is active**, routing through `buildPartialContent` instead.
Otherwise the filter is silently ignored and everything applies.

**Index drift.** After a filtered apply, indices shift: exclude hunk 3 of 5, apply 0/1/2/4, and the
surviving conflict is now index 0. The mapping is deterministic (surviving old indices, in order,
become `0..n-1`), so `remapAfterApply` is a pure function of about fifteen lines with its own test.

For any content change the selection did **not** cause, **fail closed by invalidating** the file's
entry via a content stamp. Invalidating means "everything re-ticked", which is visibly
wrong-but-safe (the user sees ticks and must press again), whereas keeping stale indices silently
excludes the *wrong* hunk. This mirrors the existing stale guard at `useGitWand.ts:1072`.

**How this fixes the live bug.** `onPreviewReject` (`MergeEditor.vue:397-401`) calls
`selection.toggle(...)` instead of mutating a ref nothing consults. `rejectedLlmHunks` folds into
the same set, generalizing away its `canResolve` special case.
`rejectedTokenMergeHunks` stays local panel state, because a `token_level_merge` is never
`autoResolved` (`assemble.ts:215-221`) and so has nothing to exclude. `autoResolutionsSummary`
filters through `shouldApply`. `ResolveAutoSummaryModal` gains a checkbox column and a confidence
badge per row. `ResolutionPreviewPanel` gains confidence props and renders a badge.

### 3.6 Surfacing confidence without noise

`PreviewHunk` gains three fields:

```ts
export interface PreviewHunk {
  startLine: number;
  type: string;
  autoResolved: boolean;
  confidenceScore: number;      // 0-100
  confidenceLabel: Confidence;  // colour without re-deriving thresholds
  reason: string;               // resolutionReason: the tooltip, and the "why manual"
}
```

Deliberately **not** `resolvedLines`: there are no checkboxes in the preview, so the panel never
needs the content, and omitting it keeps the summary small on large merges.

`PreviewFileResult` keeps its shape. Threshold-aware counts are **derived computeds**, not stored
state, so the panel stays dumb.

Rendering:

- Per hunk, a 3px coloured bar keyed on `confidenceLabel`, with the score and reason in the `title`.
  No number in the row by default.
- The number appears **only** on rows held back by the threshold, which also get a distinct icon and
  a muted style. That is the one case where the score is actionable.
- Footer: a **5-stop segmented control** (`Off / 60 / 75 / 90 / 95`), not a free slider. Scores
  cluster around a handful of dimension combinations, so a continuous 0-100 slider offers about 95
  positions that do nothing and invites exactly the false precision the `complex`-at-60 trap feeds
  on. Discrete stops are also persistable and testable.
- One summary line: "12 auto-resolvable, 3 held back by the 90% bar, 4 manual", with the tier
  breakdown from `summarizeTiers` behind a tooltip.

**Setting and per-preview override, both.** `AppSettings.resolution.minConfidenceScore` (default
`0`) is a sibling of `automations`, **not** inside `automations.autoResolve`: the bar governs every
apply path, including the merge editor's "Resolve auto" and the MERGE_HEAD automation. One bar
everywhere, or "apply only >= 90%" means three different things in three places. The panel control
is seeded from the Setting and is not persisted; it resets when the preview closes.

Per AGENTS.md the field lands in `useSettings.ts` **and** `SettingsPanel.vue`'s local `Settings`
interface in the same commit.

### 3.7 Fix the Rust preview defects now, because parity forces it

`/api/reconstruct-conflict`, the route shape to copy, already passes `-L ours -L base -L theirs`. If
the new routes copy it and Rust does not, parity fails on the marker lines. So either the routes
ship deliberately wrong, or Rust gets fixed. Fix Rust:

- **Temp-file race:** use the in-repo precedent from `git_interactive_rebase` (`ops.rs:750-754`), a
  `temp_dir().join(format!("gitwand-preview-{}-{}", process::id(), nanos))` directory with
  `create_dir_all` and `remove_dir_all` on exit. No new crate (`tempfile` is not a dependency).
- **Missing `-L` labels:** add them.
- **Rebase dedup provenance:** **defer with a ROADMAP note.** It needs a new field on the serialized
  `FileMergePreview`, rippling into parity normalization, for a UX enrichment that does not block
  apply-from-preview.

Three real dev-server routes share one `simulate3Way(cwd, ancestor, ours, theirs)` helper
(`mkdtempSync`, `git show <rev>:<path>`, `git merge-file -p --diff3 -L ours -L base -L theirs`,
`rmSync` in a `finally`) mirroring `build_3way_preview`, plus the rebase route's per-file dedup
scoring and the same sort order.

In `backend.ts`, `previewRebase` and `previewCherryPick` drop their `return []` stubs, and
`previewMerge` stops swallowing the error and **throws**. `useMergePreview` already catches into
`error.value`, so a failing predictor shows a message instead of a false "clean merge".

## 4. Half 2: the CodeMirror thread

### 4.1 Three layers

```
utils/codemirrorLibs.ts              module-level, memoized, no Vue, no reactivity
  |- composables/useCodeMirror.ts    per-instance: one EditorView + compartments
       |- components/CodeEditor.vue       thin v-model SFC   <- MergeEditor, DiffViewer
       |- components/FileExplorerPanel.vue  keeps its own tab cache, does NOT use CodeEditor.vue
```

**`utils/codemirrorLibs.ts`** lives in `utils/`, not `composables/`, because it holds no reactive
state: the same rationale as `utils/highlight.ts`, the same memoized-dynamic-import shape as
`utils/coreEngine.ts`.

```ts
export function loadCodeMirror(): Promise<CmLibs>   // memoized: the single Promise.all of 5 imports
export function peekCodeMirror(): CmLibs | null     // sync, for guards and tests
export function detectLanguageExtension(path: string): Promise<Extension[]>  // memoized per extension
```

Two improvements over today: the promise is memoized so consumers 2 and 3 never re-await, and
language detection memoizes per extension (today every tab re-imports `language-data` and re-loads
the grammar).

All `@codemirror/*` imports in the new files are **`import type` only**, the pattern already at
`FileExplorerPanel.vue:11-12`. Erased at build, zero bundle reachability.

**`composables/useCodeMirror.ts`** owns exactly one `EditorView` and four compartments.
`buildState` and `mount` stay **separate**, which is what lets `FileExplorerPanel` keep its
`docStates` cache and all five "did the active tab change while we awaited?" re-checks
(`:295, :299, :311, :316, :346`) in the component, unchanged. The composable never learns about
tabs; if it did, either it grows a tab concept (wrong) or the File Explorer loses its cache (a
regression).

`reconfigure(compartment, ext)` stays generic so the blame gutter stays in the component.
`useBlameGutter.ts` is deliberately CodeMirror-free and that boundary is worth keeping.

No reactive `doc` prop at this layer: the doc is imperative (`setDoc` / `getDoc`), and `v-model`
semantics live one layer up. Mixing them here produces the classic echo loop.

**`components/CodeEditor.vue`** is the thin `v-model` SFC. Two things a naive implementation gets
wrong:

- Inbound sync must be `watch(() => props.modelValue, v => { if (v !== getDoc()) setDoc(v) })`. The
  `!==` guard is what terminates the round trip; the outbound side emits only on
  `update.docChanged`.
- `ariaLabel` and `spellcheck` go through `EditorView.contentAttributes`, not a wrapper div: the
  contenteditable is what a screen reader focuses.

`minLines` / `maxLines` map to CSS on `.cm-editor` with `overflow: auto` on `.cm-scroller`, not to
extensions.

### 4.2 Fix the theme now

Today `oneDark` is unconditional. That reads as deliberate chrome while the editor fills a whole
pane, the way a terminal is dark. The moment CodeMirror appears as a *box inside* the merge editor's
hunk stack and inside a diff table row on a light-themed app, it stops being chrome and becomes a
rendering bug. The blame-gutter CSS comment at `:818-822` is already an admission that the
hardcoding leaks.

It is cheap:

- `basicSetup` already includes `syntaxHighlighting(defaultHighlightStyle)`, so on light we simply
  **do not add `oneDark`** and get a correct light token palette for free. Zero new dependency, and
  the 2 KB `theme-one-dark` chunk stays lazy for the dark case.
- The light chrome is one `EditorView.theme({...}, { dark: false })` of about 25 declarations
  referencing the app's own `--color-*` custom properties, so it self-tracks the design tokens.
- A `themeCompartment` in `useCodeMirror`, reconfigured from `watch(theme)`.

Consequence: the hardcoded `#282c34` / `#7d8799` / `#21252b` at `FileExplorerPanel.vue:804-835`
become design tokens and the justifying comment is deleted. This is the **only** intentional
behavioural change to the File Explorer in this thread; everything else must be behaviour-identical.

No new setting. `useTheme()` is the single source.

### 4.3 Migrating the File Explorer

Same release, **separate task, immediately after the extraction**.

Not the same task as the extraction, because a reviewer reading one diff that both introduces an
abstraction and rewrites its first consumer cannot tell which line caused a behaviour change. Not a
follow-up release either, because leaving the File Explorer on a duplicated copy for a version means
the extraction is validated only by two new consumers whose requirements are strictly simpler: the
tab cache, the blame gutter and the async re-check pattern would all go untested.

The safety net is `FileExplorerPanel.test.ts`, which does not exist today and is the single largest
test gap in this area. Written the house way: jsdom docblock, native `createApp` (there is no
`@vue/test-utils` in the tree), `vi.mock("../../utils/backend")` for the file I/O. Sixty existing
test files already mock `backend`, and this is not "mocking git" in the AGENTS.md sense because no
git behaviour is under test.

Six assertions, chosen to cover exactly what the extraction could break: mount, the `docStates`
cache (edit A, switch to B, back to A restores the *edited* doc), the dirty-sync listener, the
editable re-assert on a cached state predating a lock toggle, blame invalidation via
`queueMicrotask`, and a theme swap.

### 4.4 MergeEditor swap

`MergeEditor.vue:1059-1065` becomes a `<CodeEditor>` with `:key="seg.hunkIndex"`,
`v-model="editContent"` and `:file-path="file.path"`, imported via `defineAsyncComponent`.

`validateEditing` (`:73-77`) and `resolveHunkCustom` (`useGitWand.ts:1061-1077`, with its
`contentAtCall` staleness bail) are **unchanged**. That is the whole point of `v-model`: the
write-back path never learns that the widget changed.

**Async, not static, and this does not contradict the comment at `MergeEditor.vue:25-28`.** That
comment justifies statically importing `ResolveAutoSummaryModal` because it is a thin BaseModal
wrapper with no heavy deps. `CodeEditor` is the opposite: it is the gateway to about 400 KB, behind
a `v-if` on a default-null flag, which is verbatim the `apps/desktop/CLAUDE.md` rule. Say so in the
PR body so nobody later "fixes" the apparent inconsistency.

**The `:key` is a correctness fix, not cosmetics.** `requestAISuggestion` can set `editingHunkIndex`
to a *different* hunk while a box is open. Without the key, Vue patches the existing component and
CodeMirror's undo history survives across hunks, so enough Cmd+Z could resurrect hunk *i*'s text
into hunk *j*'s `resolveHunkCustom` call. That is a data-corruption class bug. Docs here are tiny,
so remounting costs nothing.

**The AI-prefill path is the likeliest regression.** `requestAISuggestion:101-102` sets
`editContent` *then* `editingHunkIndex`. When the box is already open on the same hunk, only the
inbound watch makes it work; a "seed the doc on mount only" implementation breaks it silently, and
no test covers it today. It gets its own assertion.

`rows="8"` becomes `:min-lines="8"` and `:max-lines="24"`. **`resize: vertical` is dropped** and
that is an accepted, documented regression: a CodeMirror view inside a user-resizable box fights its
own measurement loop, and max-lines plus scroll covers what the drag handle served. Note it in the
CHANGELOG.

The `aria-label` is today a hardcoded English template literal, an existing i18n violation on the
very line being edited. It moves to `mergeEditor.editAriaLabel` in all five locales in the same
commit.

### 4.5 Editable diff: narrow subset, full UI

**Alternatives considered.** `@codemirror/merge`'s `unifiedMergeView` is a new dependency over the
50 KB bar that discards word-diff, the collapse machinery, `origIdx`-keyed partial staging, inline
finding rows, the minimap and hunk nav all at once: a v3.13-scale rewrite, not a v3.11 bullet.
"Open the file in a full-file editor overlay" is honestly 80% of the value at 20% of the risk, but
the roadmap's operative clause is "where you see it, *without switching*", and that is switching. It
remains the graceful degradation if the release runs out of time, not the plan.

The chosen approach reuses the `colspan` escape row that already exists and is proven in this exact
table (`DiffViewer.vue:724-742`), **including its documented trap** (`:716-723`: a `<td>` with
`display: flex` stops being a table cell and the browser silently ignores `colspan`).

**The subset that ships, precisely:**

1. **Inline mode only.** Side-by-side shows a disabled pencil with a tooltip. SBS has no
   single-column text substrate, and two editors side by side *is* the rejected rewrite.
2. **Working-tree, unstaged, non-conflicted files only.** `DiffViewer` gains `editable?: boolean`,
   default **false**, so `SplitCommitModal.vue:296` passes nothing and is byte-identical in
   behaviour. Staged diffs are excluded because the rendered diff is index-vs-HEAD: editing the
   working-tree file would not change what you are looking at, which is worse than not offering it.
   Conflicted files belong to `MergeEditor`. Commit diffs never reach `DiffViewer` outside
   `SplitCommitModal` (`CommitDiffViewer` and `FileHistoryViewer` are separate components, untouched).
3. **One hunk at a time, new side only.** The editor is seeded with the hunk's post-image: every
   context and add line in order, deletes omitted, which is exactly working-tree lines
   `[newStart, newStart + newCount)`. Editing one hunk bounds every invalidation problem at once,
   because the rest of the diff is frozen while it is open.
4. **Write-back is `writeFile`, not a synthesized patch.** On confirm: fresh `readFile`, verify the
   on-disk slice still equals the post-image we seeded from, splice, write. The staleness guard
   mirrors `resolveHunkCustom`'s exactly. Building a valid unified patch from arbitrary edited text
   means re-diffing the hunk, and an apply failure surfaces as an opaque backend error; `writeFile`
   is what `saveFile` and the File Explorer already do, and it keeps the honest mental model that an
   edit is a working-tree change you stage afterwards like any other.
5. **Logic in a pure composable** `composables/useDiffEdit.ts` (`hunkPostImage`, `spliceHunk`), per
   the house rule preferring composable tests. `spliceHunk` reconstructs from the original string so
   the file's dominant EOL and its trailing-newline-or-not survive; never a bare `split("\n")`
   round trip.
6. **Invalidation is free.** On confirm the component emits, App.vue writes and calls
   `repoRefresh()`, `props.diff` changes, and the **existing** watch at `:377-380` clears
   `lineSelection` while `allLineTypes` recomputes so the minimap redraws. No new machinery.
7. **Findings drift is accepted and documented.** Findings are index-scoped (`App.vue:315`), so a
   working-tree edit cannot legitimately move them, and the `stagedFingerprint` watcher
   (`App.vue:1474`) rescans on the next stage. A CHANGELOG note, not a line-mapping layer.

Affordances: syntax highlighting, line numbers, undo inside the box, Esc cancels, Cmd/Ctrl+Enter
confirms. No blame gutter, no autocompletion beyond `basicSetup`'s.

### 4.6 The #128 follow-up, and the correctness trap inside it

`onRebaseConflict()` (`App.vue:3827-3838`) sets `showRebase = false`, `RebaseEditor` unmounts, and
with it `pendingSplitAtHead` and `handleSplitAtHead`. Only the banner's Abort / Skip / Auto-resolve
/ Continue survive.

**A literal "put the Split button back on the conflict banner" is wrong.**
`useSplitCommit.openFor` requires HEAD to be the commit being split, and `gitSplitCommit` does
`reset --mixed HEAD^`. At a rebase **conflict** halt the conflicting commit has not been created
yet: HEAD is its parent. A Split button there would split the previous commit.

The resolution is also what makes the feature simple. GitWand's synthetic `split` action serializes
into the rebase todo as `edit` (`useInteractiveRebase.ts:60-72`), and git's `edit` stop happens
**after** the commit is created. So a commit marked `split` that also conflicts will, once the user
resolves and continues, land on its own `edit` stop with HEAD on the freshly created commit, with
`RebaseEditor` still unmounted and the banner as the only surface. **That is precisely where the
button belongs and where it is correct.**

Rule: show it when `pendingSplit && !repoState.hasConflict`. `RebaseProgressBanner.vue:63` already
renders a distinct `--ready` state for exactly that condition.

Wiring: the button goes in `.rpm-actions` immediately left of Continue, with Continue demoted to
neutral while it shows (mirroring `RebaseEditor.vue:459-462`). The banner stays presentational, so
it gains a `pendingSplit?: boolean` prop and a `split` emit. It **reuses the existing
`rebase.splitThisCommit` key**, verified present in all five locale files, so there is **zero new
i18n work**.

Add a sibling free export `getPendingSplitForHash(hash)` in `useInteractiveRebase.ts` and have the
existing `getPendingSplitAtHead` delegate to it, so the prefix-matching logic is reused verbatim and
cannot drift. App.vue then computes `pendingSplitAtHalt` and relocates `handleSplitAtHead`, calling
`gitRebaseAction(cwd, "continue")` directly rather than the composable's `rebaseContinue`, to stay
on the banner's own action path and avoid instantiating a second `useInteractiveRebase`.

**The one blocking unknown.** `getPendingSplitForHash` matches the commit being replayed.
`RepoOperationState.operationHead` is rendered by the banner as `shortHead` next to the target
branch (`RebaseProgressBanner.vue:36-40`), which *reads* like the replayed commit, but that is
inference, not verification. **Confirm it first** against `refreshRepoState` (`App.vue:2476-2490`)
and the Rust `repo_operation_state` command versus `REBASE_HEAD`. If it turns out to be the branch
tip, the fix needs a new field on `RepoOperationState`, therefore a Rust command change plus a
`backend.ts` wrapper plus a dev-server route plus a parity test in the same PR. In that case,
**defer this task rather than rush it.**

**Do not wire `EditCommitOverlay`.** It is driven by `editingCommit` from the commit-log context
menu, and `RebaseEditor` never opened it, so it was not lost in the #128 handoff. "Re-surfacing" it
is new scope. If the "edit affordance" half of the roadmap sentence is wanted, the correct reading
is *amend at an `edit` stop*, and it should ship as an optional follow-up after verifying that
`handleAmendConfirm`'s surrounding refresh logic is rebase-safe.

### 4.7 Bundle rules, non-negotiable

```
App.vue        defineAsyncComponent -> MergeEditor / DiffViewer / FileExplorerPanel   (already true)
  |- each SFC  defineAsyncComponent -> CodeEditor.vue                                 (new, both)
       |- codemirrorLibs.ts   memoized Promise.all of 5 dynamic import()
            |- language-data  per-language dynamic import()                           (already true)
```

Four levels. `FileExplorerPanel` is the existing two-level precedent and this extends it. Opening
the merge editor costs nothing; clicking Edit costs the 400 KB once, process-wide, for all three
surfaces.

Budgets hold, thinly: main is unaffected **if and only if** nothing statically reachable from the
entry imports a CodeMirror *value*, enforced by `import type` plus `defineAsyncComponent` at all
call sites. The binding constraint is `SplitCommitModal` plus `DiffViewer` sharing a chunk.

**Re-baseline the budget comment in its own task**, never inside a feature PR. A budget raised in
the same diff as the feature that needed it is a budget that has stopped meaning anything, which is
exactly what the comment at `bundle-check.mjs:88-90` warns about. The five locale chunks (about
381 KB total) are the obvious prune target if headroom is wanted back.

## 5. Risks

1. **Estimate/actual divergence is intrinsic** and cannot be engineered away. Section 3.2 closes the
   largest contributor; the rest are named in the drift message. A button labelled with a number
   that turns out wrong is the single biggest product risk in this release.
2. **Positional index remapping is the highest-risk code in Half 1.** Mitigated by a pure function,
   a dedicated unit test and fail-closed content stamps. A pre-existing subtlety to pin while there:
   `buildPartialContent` matches resolutions to markers positionally, so any divergence between the
   resolution list and the marker walk silently applies the *wrong* resolution.
3. **Switching the preview to `resolveAsync` moves existing numbers.** Some files flip `partial` to
   `auto-resolved`. That is the feature working, not a regression, but it must be called out.
4. **`complex` at 60 stays a latent trap** for anyone who later makes the numeric gate a
   replacement rather than an addition. Mitigated by a named footgun test and a comment at both gate
   sites.
5. **18 KB of main headroom.** An accidental static import is a hard CI failure, which is the *good*
   outcome. The bad outcome is someone quietly raising the budget.
6. **Splitting the wrong commit** is the highest-severity correctness item in Half 2. Gated on
   `!hasConflict`, and blocked on verifying `operationHead`.
7. **Stale undo history across hunks** in MergeEditor if the `:key` is omitted.
8. **FileExplorerPanel has no test today** and its safety net arrives in the same task that rewrites
   it. Sequencing that task before the two new consumers is the mitigation.
9. **Snapshot capture returns `null` on a repo with no HEAD**, so the escape hatch is silently
   absent. Surface `snapshotId: null` in the report.
10. **Long merges** are N worker round trips serialized by `withFiles`. The button needs a progress
    state, and there is deliberately **no cancel**: a mid-flight cancel would leave a half-applied
    merge.
11. **CodeMirror in jsdom** may need a `Range.prototype.getClientRects` shim. Any shim goes in a
    local `src/test-utils/` helper, **never** in `src/test-setup.ts`, which runs for all 133 test
    files including node-env ones and must not touch `document`.
12. **`repo_lock::write` contention**: the orchestrator issues several write-locked git commands in
    sequence while the status poller and the rebase-state interval run. Not new, but denser.

## 6. Non-goals

No new npm dependency of any kind, specifically not `@codemirror/merge`. No editable diff in
side-by-side, staged, commit, PR, file-history or split-commit views; no binary or image diffs; no
hunk from a diff truncated by the 5 MB cap; no multi-hunk or multi-file simultaneous editing; no
"stage the edit directly as a partial patch". No per-hunk opt-out in the preview panel (unsound).
No LLM call inside a preview. No rebase-commit provenance in `FileMergePreview` (deferred, noted in
ROADMAP). No `DiffViewer` virtualization rewrite. No `MergeEditor` redesign beyond the textarea
swap. No `EditCommitOverlay` wiring. No blame gutter in the merge or diff editors. No
`resize: vertical` parity. No editor-theme setting. No new `SnapshotMeta["kind"]`. No undo of a
finalized merge beyond the existing Time Machine. No new Rust conflict-resolution logic: the engine
is TypeScript-only. And none of the other seven v3.11.0 lots.
