# v3.13.0 Agent Workspaces I — lifecycle & merge-back: design

**Date:** 2026-11-04
**Roadmap:** `roadmap.md` § "v3.13.0 — Agent Workspaces I: lifecycle & merge-back"
**Out of scope:** everything the roadmap puts in v3.16.0 (agent status, permission requests, agent picker, worktrees view, cross-worktree conflict prediction, merged-PR cleanup). See §11.

The user asked for this spec to be written straight from the roadmap, without a question round. Every decision the roadmap does not make is marked **(spec call)**. Those are the ones to check while reading.

## 1. What exists today

All paths are under `apps/desktop/` unless they start with `packages/`.

**Two creation paths, two directory conventions.**

| Path | Creation | Base | Directory |
|---|---|---|---|
| Worktree manager | `WorktreeManager.vue` calls `git_worktree_add(cwd, path, branch, new_branch)` (`src-tauri/src/commands/ops.rs:2811`) | Whatever the form passes. Quick-create passes an **empty base** (`WorktreeManager.vue:83-101`). | `<repo>.worktrees/<slug>` |
| AI task | `App.vue:2363 createAiTaskScratchWorktree` calls `scratch_worktree_create` (`src-tauri/src/commands/scratch.rs:142`) | The local `HEAD`, recorded as `branch.<b>.gitwandBase` / `gitwandSource` | Sibling `../gitwand-scratch-<slug>` |

Neither path fetches first. Neither runs anything after creation. The AI task then opens a terminal on `claude` (`App.vue:2392`).

**Merge-back** (PR #233, `scratch_worktree_merge_back_impl`, `scratch.rs:378-564`):
- It runs under the repo write lock.
- It refuses unless all of these hold:
  - the main checkout's `HEAD` is an ancestor of the task;
  - the main checkout is still on the recorded source;
  - nothing is mid-operation;
  - the dry-run `read-tree` finds no overlap.
- It commits the task's outstanding work and snapshots the **main checkout**.
- It finishes with `git merge --squash --ff-only`.
- The result is staged and uncommitted, so the agent's commits are flattened. As soon as `main` has moved, it refuses, which is the normal case for a long agent task.

**Removal:**
- `git_worktree_remove` (`ops.rs:2874`) runs `git worktree remove [--force]`.
- The AI-task close flow (`App.vue:2603-2658`) disposes the repo's terminal tabs, then removes the worktree with `force=true` and deletes the branch.
- No teardown and no snapshot, on any path.
- A lock is respected only because a single `--force` happens not to override it.

**Stopping processes** (`terminal_close`, `src-tauri/src/commands/terminal.rs:300-419`):
- **Unix:** sends SIGHUP and then SIGKILL to the leader's process group and to the foreground job group. Background jobs, `setsid` processes and a foreground job whose leader already exited survive; the comment at line 360 says so.
- **Windows:** kills only the leader (`terminal.rs:340`).

**Preview → apply** (v3.11):
- `preview_merge` / `preview_rebase` (`src-tauri/src/commands/read.rs:1765`, `:1971`) simulate against the `HEAD` of a given `cwd`.
- `useApplyFromPreview.ts:190` applies a merge, rebase or cherry-pick. It snapshots, auto-resolves, stages and continues.
- It is wired once, in `App.vue:914-970`, bound to the open repo.

**Snapshots** (`src-tauri/src/git/snapshot.rs`):
- What is captured:
  - `HEAD`, the index, the working tree and untracked files;
  - **not** ignored files;
  - no worktree path in the metadata.
- The refs live in the shared `refs/gitwand/snapshots/`, so a snapshot taken in a linked worktree outlives the worktree.
- Restore works in place only.

**`.gitwandrc`:**
- It is **JSON**. `parseGitwandrc` (`packages/core/src/config.ts:398`) runs `JSON.parse` and drops unknown keys.
- The Rust side returns the raw text (`read_gitwandrc`, `ops.rs:4673`).
- Nothing in the codebase runs a user-defined command. `utils/gitwandHook.ts` only generates GitWand's own pre-commit hook.

**Terminal:**
- `terminal_open(cwd, shell?, agent?, cols, rows, on_output)` (`terminal.rs:99`) has no command, no argument list and no environment parameter.
- It reports no exit code: the end of a session is only seen as an EOF on its output.

**Dev-server:**
- `/api/git-worktree-add` and `/api/git-worktree-remove` build their command with `execSync` and string interpolation (`dev-server.mjs:7672`, `:7697`), which `AGENTS.md` forbids.
- Merge-back and discard are `desktopOnly` gaps in `utils/commandRegistry.ts:343-350`.

## 2. Intent

A worktree stops being a bare git checkout and becomes an **environment that the repo knows how to bring up and tear down**. Agent work in it comes back as **real commits through the same preview → apply flow** as any other merge.

The test case is Dendreo's `bin/worktree`. Each worktree has its own containers, subdomain, tenant, test databases and Vite port. Removing a worktree from GitWand today orphans all of them.

**Success looks like this.** On a repo with a `worktree` section, these all happen without leaving GitWand and without orphaning anything:
- create a task worktree;
- watch `setup` run;
- open its URL;
- let an agent work while `main` moves on;
- bring the work back with the agent's commits intact;
- remove the worktree.

**Anti-goals.** Shipping any of these would make the release a failure, even if every feature works:
- GitWand runs a repo's commands without the user ever agreeing to it.
- A removal goes through when teardown failed, or when a process still runs in the worktree, unless the user explicitly overrode it.
- A worktree that is locked, marked `.worktree-keep` or owned by another tool is removed or modified.
- Merge-back loses work: uncommitted files in the task, agent commits, or local changes in the main checkout.

---

## 3. One worktree service

Both creation paths (worktree manager and AI task) and every removal path (manager delete, AI-task close, merge-back cleanup, discard) go through **one** Rust module, `src-tauri/src/worktree/`, exposed by a small set of commands (§10). `scratch.rs` keeps its merge logic but calls this module for creation and removal. The goal is that there is only one place where teardown, guards and snapshots can be skipped. **(spec call)**

A worktree created by GitWand is recorded in `$GIT_COMMON_DIR/gitwand/worktrees.json`. That file is shared by every worktree of the repo and never committed. Each record holds:
- path;
- branch;
- base ref and base commit;
- creation time;
- `kind` (`task` | `manual`);
- the source branch.

This record is what "owned by GitWand" means in §7. It replaces `branch.<b>.gitwandBase` / `gitwandSource`, which are still read for worktrees created before v3.13. **(spec call)**

## 4. Configuration: the `worktree` section

### Format

`.gitwandrc` stays JSON. The roadmap's YAML block shows the shape, not the syntax. Adding a YAML parser to `packages/core` for one section is not worth it, and would make the file accept two syntaxes. **(spec call)**

```json
{
  "worktree": {
    "dir": ".claude/worktrees",
    "include": [".env", "auth.json", { "path": ".claude/settings.local.json", "mode": "symlink" }],
    "setup": "bin/worktree provision {name}",
    "teardown": "bin/worktree teardown {name}",
    "url": "bin/worktree url {name}"
  }
}
```

| Key | Type | Default | Meaning |
|---|---|---|---|
| `dir` | string, relative to the repo root or absolute | `<repo>.worktrees` (sibling) | Where new worktrees go. Existing worktrees elsewhere keep working. |
| `include` | array of `string` or `{ path, mode: "copy" \| "symlink" }` | none | Ignored files and folders to bring into a new worktree (§5.3) |
| `setup` | string | none | Runs after creation (§5.4) |
| `teardown` | string | none | Runs before any removal (§7.2) |
| `url` | string | none | Prints the environment's URL on stdout. Its first non-empty line is shown on the worktree. |

`parseGitwandrc` gets a typed `worktree` field and a validator in the same style as the other keys:
- an invalid entry is dropped and a warning is logged;
- a relative `dir` is resolved against the main worktree root.

**Default directory.** The default moves both paths to `<repo>.worktrees/<slug>`, the manager's current convention. The AI task's sibling `gitwand-scratch-*` goes away for new worktrees. **(spec call)** `.claude/worktrees` is what Dendreo writes in its own config. It is not the default, because putting worktrees inside the repo needs a `.gitignore` entry that GitWand should not add on its own.

**`.worktreeinclude`.** If the file exists at the repo root, its lines are added to `include` (copy mode). It uses the `.gitignore` pattern syntax, the same convention as Claude Code, Conductor and Strand. If both are present, the union is used.

**Which copy is read.** Settings come from the **main worktree's** `.gitwandrc`, read at the moment of the operation, never from the task worktree's copy. Otherwise an agent could rewrite `teardown` inside the worktree it is about to have removed. **(spec call)**

### Placeholders and environment

Placeholders in `setup`, `teardown` and `url`:
- `{name}`: the worktree slug, restricted to `[a-z0-9][a-z0-9-]{0,62}`;
- `{path}`, `{branch}`, `{base}`: each substituted **shell-quoted**.

The same four values are also exported as `GITWAND_WORKTREE_NAME`, `GITWAND_WORKTREE_PATH`, `GITWAND_WORKTREE_BRANCH` and `GITWAND_WORKTREE_BASE`, plus `GITWAND_REPO_ROOT` (the main worktree). Each command runs with the new worktree as its working directory, through the user's login shell: `$SHELL -lc` on Unix, `cmd /C` on Windows.

The command string comes from the repo, so running it through a shell is intended. The placeholders are the only values GitWand puts into it, and they are quoted. This does not break the `AGENTS.md` rule on interpolation, which concerns GitWand-built git commands.

### Trust

A `.gitwandrc` arrives with `git clone`, so running its commands silently would hand a repo arbitrary code execution. The first time the user creates or removes a worktree in a repo whose `setup` / `teardown` / `url` are set, GitWand shows a confirmation dialog:
- it shows the three commands verbatim;
- it offers **Trust and run**, **Skip hooks this time** and **Cancel**;
- the trust it grants is stored per repo, together with the SHA-256 of the canonical JSON of those three strings, in GitWand's app data (not in the repo);
- any change to the strings asks again.

`include` needs no trust, because it only copies the user's own files. **(spec call)**

## 5. Creation

### 5.1 Entry points

- **AI task** (the current `AiTaskNameModal` flow): the user gives a name, the worktree is created on `task/<name>`, the agent is launched.
- **Worktree manager:**
  - Quick-create keeps its single name field.
  - The full form keeps path, base and branch, and pre-fills the path from `dir`.
  - Quick-create's empty-base bug disappears, because the base now has a resolved default (§5.2).

### 5.2 Base

The default base is the **freshly fetched remote default branch**:
1. Run `git fetch <remote> <default>` on the remote of the current branch's upstream, or `origin` when there is none.
2. Use `refs/remotes/<remote>/HEAD`. If that is missing, try `<remote>/main`, then `<remote>/master`.
3. If the fetch fails (offline, auth), fall back to the local tracking ref, then to the local `HEAD`. The creation dialog shows which base was used and why: "based on origin/main fetched 2 s ago", or "offline: based on local main".

The user can always pick another base: a local or remote branch, or the current `HEAD` (the pre-v3.13 behavior).

The new branch is created **without upstream tracking**, so that `git push` from the task does not push to `main`. **(spec call)**

### 5.3 Include

After `git worktree add`, each `include` entry is resolved against the main worktree:
- **Only ignored paths are processed**, checked with `git check-ignore`. A tracked path is skipped with a warning, because the checkout already has it.
- A missing path is skipped silently.
- `copy` copies files and folders recursively. `symlink` creates a link to the main worktree's path.
- On Windows a symlink that fails (no developer mode) falls back to copy and shows a warning.
- Paths must stay inside the repo: an entry that resolves outside it, through `..` or a link, is refused.

### 5.4 Setup

`setup` runs in a **dedicated, read-only terminal tab**, labeled "Setup · <name>":
- Its output streams in live.
- The tab ends on an exit line: ✓ on 0, or ✗ with the exit code otherwise.
- On success, `url` runs (output captured, not shown in a tab), and the URL appears on the worktree with an "Open" action.
- On failure, the worktree is kept. Its card shows "Setup failed", with **Retry setup**, **Open the log** and **Remove** (which goes through teardown, §7).

The agent is launched **after** setup succeeds. When there is no `setup`, it is launched right away. On failure the agent is not launched; the user can launch it by hand. **(spec call)**

This requires a new terminal mode (§10.2): run a given command with a given environment, and return its exit code.

### 5.5 Agent launch

v3.13 keeps launching Claude Code, as today. The agent picker is v3.16.

## 6. Bringing work back

### 6.1 Flow

The user starts it from "Merge back" on an AI task, which replaces the current merge button, or from the worktree manager on a GitWand-owned worktree.

1. **Choose.**
   - **Target:** the recorded source branch by default, otherwise the base's local branch.
   - **Mode:**
     - **Merge** (default): a merge commit on the target, so the agent's commits are kept.
     - **Rebase**: the agent's commits are replayed onto the target, then the target fast-forwards; linear history.
     - **Squash**: today's behavior, the changes staged on the target, uncommitted, for the user to write the commit message.
2. **Check the main checkout.** It must be on the target branch, with nothing in progress and no change that overlaps the task's files. Otherwise GitWand refuses, explains why and does nothing. It never stashes automatically.
   - If the main checkout is on another branch, GitWand offers to switch it, which is only possible when it is clean.
   - Unrelated local changes do not block a merge. They are protected by the snapshot and by git's own refusal to overwrite.
3. **Stop the task's processes** (§8). This step is required: an agent still writing during a merge is the risk this whole flow guards against.
4. **Commit outstanding task work.**
   - What it commits: any uncommitted change in the task worktree, tracked or untracked but not ignored.
   - The commit message is `wip(<name>): uncommitted work at merge-back`.
   - It is made with hooks and signing disabled, as today.
5. **Snapshot both sides:**
   - the task worktree (`kind: merge-back-task`);
   - the main checkout (`kind: merge-back`).
6. **Preview**, using the v3.11 `MergePreviewPanel`:
   - Merge and squash run `preview_merge`, with `cwd` set to the main checkout and the task branch as the source.
   - Rebase runs `preview_rebase`, with `cwd` set to the **task worktree** and the target as `onto`.
   - The panel shows the confidence bar and the conflicts the engine would auto-resolve.
7. **Apply**, after the user confirms, through `useApplyFromPreview`:
   - Merge: `git merge --no-ff --no-edit <task>` in the main checkout.
   - Rebase: `git rebase <target>` in the task worktree, then `git merge --ff-only <task>` in the main checkout.
   - Squash: the current path, but it no longer needs `HEAD` to be an ancestor of the task: `git merge --squash <task>` with auto-resolution.
   - Conflicts the engine leaves unresolved open in the normal resolution view, in the right checkout. **Nothing is ever aborted automatically.** Abort is an explicit action, and the snapshots make it reversible.
8. **Clean up.** Once the target holds the result (merge commit or fast-forward done, or squash staged), GitWand offers to remove the task worktree through §7. It does not remove it automatically, so the user can check first. **(spec call)**
   - The task branch is deleted only once it is fully merged, which is never true after a squash. For a squash, the dialog explains this and asks.

### 6.2 What it takes

- `useApplyFromPreview` needs one instance per checkout. Its dependencies (`cwd`, `refresh`, the source of conflicted paths) are passed in instead of read from the open repo. The existing instance in `App.vue` becomes the one bound to the open repo. **(spec call)**
- When the checkout being operated on is not the open tab (for example, rebase in the task worktree), GitWand opens or focuses that checkout's tab for the duration of the conflict step. It does not show conflicts from a checkout the user is not looking at.
- The current refusal "main moved, merge main into the task first" disappears. The pre-flight guards in §6.1 step 2 replace it.

## 7. Removal

### 7.1 Guards: never touch

A worktree is **untouchable** when any of these holds:
- it is locked (`git worktree lock`);
- `.worktree-keep` exists at its root;
- it is not owned by GitWand (§3) **and** it lives under another orchestrator's known directory: `.claude/worktrees/` when no GitWand record exists, Conductor's workspaces, Superset's. That list lives in one Rust constant.

For an untouchable worktree:
- **Remove**, **merge-back cleanup** and **discard** are disabled, with the reason shown.
- The only offered action is the specific unlock (**Unlock** for a git lock), which the user must take separately before removing.
- GitWand never deletes a `.worktree-keep` file.
- `git worktree remove` is never passed `--force` twice.

A worktree that GitWand does not own but that is not untouchable (one created by hand, for instance) can be removed manually after an extra confirmation that names it as not created by GitWand. **(spec call)**

### 7.2 Sequence

Every removal follows this order, whatever its trigger:
1. Guards (§7.1).
2. Stop the processes (§8). If any survive, they are listed and removal is blocked.
3. **Snapshot** the worktree (`kind: removal`, §9).
4. **Teardown**, if one is set and trusted:
   - It runs in a read-only terminal tab, like setup.
   - **A non-zero exit blocks the removal.** The worktree stays, marked "Teardown failed", with **Retry teardown**, **Open the log** and **Remove anyway**.
   - **Remove anyway** asks for a second confirmation that names what may be orphaned (containers, databases, whatever the script manages).
5. `git worktree remove` (with `--force` only once the snapshot exists), then `git worktree prune`.
6. Delete the branch, only for `kind: task` worktrees whose branch is merged, or when the user ticked "Also delete branch".
7. Drop the record from `worktrees.json`.

If the user chose **Skip hooks this time** at the trust prompt, step 4 is skipped, and the dialog warns that teardown did not run.

## 8. Stopping a worktree's processes

**Goal:** after this step, no process GitWand started for the worktree survives, and no process at all has its working directory inside it.

**At spawn:**
- On Unix, every PTY session (agent, shell, setup) becomes the leader of its own session (`setsid`), as today. GitWand records its session id.
- On Windows, every PTY child is assigned to a **Job Object** with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`. Closing the job then kills the whole tree, including grandchildren.

**On stop:**
1. **Unix:** SIGHUP to every process whose session id matches a recorded one. This covers background jobs and orphaned foreground jobs, but not processes that called `setsid` themselves.
2. **Windows:** terminate the job.
3. After 500 ms, **sweep by working directory**: list the processes whose working directory is inside the worktree path (`lsof -d cwd` on macOS, `/proc/*/cwd` on Linux, as `active_cwds_for_tool` in `ops.rs:3749` already does; process snapshot APIs on Windows).
   - Those GitWand started (same session, or a descendant) get SIGTERM, then SIGKILL after 2 s.
   - Others are **not killed**: they are listed, and the operation blocks with "These processes are still running in this worktree" (pid, name) and **Retry**.
   - The user can stop them with **Stop all**, which requires an explicit click. **(spec call)**
4. Close the terminal tabs registered for the worktree path, not only for the repo key.

The dev-server mirrors steps 1–2 with node-pty's process tree as far as Node allows. Its route is documented in the command registry as a best-effort mirror for manual QA.

## 9. Snapshot and restore

- `create_snapshot_inner` gets optional metadata: `worktree_path`, `worktree_branch`, `worktree_name`. It is stored in the existing JSON subject, so the format stays backward compatible.
- Ignored files are **not** captured. `include` files come from the main worktree and are copied again on restore. Other ignored state (containers, databases) belongs to `teardown`. The removal dialog says this. **(spec call)**
- **Restore as a new worktree:**
  - It is offered from the snapshot list for snapshots with `kind: removal` or `merge-back-task`.
  - It creates a worktree at `<dir>/<name>-restored`, with branch `restore/<name>`, from the snapshot's `HEAD`.
  - It then checks out the snapshot's working tree and index on top, using the same mechanics as the in-place restore.
  - It then runs `include` and, if trusted, `setup`.
  - It is recorded as `kind: task`, with the original base.
- Pruning follows the existing snapshot retention.

## 10. New and changed backend surface

### 10.1 Commands

All of them use `safe_repo_path` on every user-supplied path. Each has a typed wrapper in `utils/backend.ts` and an entry in `utils/commandRegistry.ts`.

| Command | Replaces / extends | Notes |
|---|---|---|
| `worktree_create(cwd, name, base?, branch?, path?, kind)` | `git_worktree_add` (kept for compatibility, then calls it), `scratch_worktree_create` | Fetches the base, runs include, writes the record. Does **not** run `setup`; the frontend opens the setup tab. |
| `worktree_resolve_base(cwd)` | (new) | Returns `{ref, commit, fetched_at, fallback_reason}` for the dialog. |
| `worktree_guard(cwd, path)` | (new) | Returns `{untouchable: bool, reasons[], owned: bool}`. |
| `worktree_stop_processes(cwd, path, kill_foreign: bool)` | (extends `terminal_close`) | Returns the survivors. |
| `worktree_remove(cwd, path, opts)` | `git_worktree_remove`, `remove_scratch`, `scratch_worktree_discard` | Runs §7.2 steps 1–3 and 5–7. Teardown is run by the frontend through 10.2, and its exit code is passed in. Refuses unless teardown succeeded, was skipped, or the user confirmed removing anyway. |
| `worktree_url(cwd, path)` | (new) | Runs `url` and returns its first non-empty line. 10 s timeout. |
| `worktree_hooks_trust(cwd)` / `worktree_hooks_trust_set(cwd, hash)` | (new) | Trust store in app data. |
| `snapshot_restore_as_worktree(cwd, id, name)` | (new) | §9 |
| `worktree_merge_back_prepare(cwd, path)` | `scratch_worktree_merge_back` | §6.1 steps 2 and 4–5. Returns the snapshots. Preview and apply go through the existing commands. |

### 10.2 Terminal

`terminal_open` gets optional `command: Option<String>` and `env: Option<HashMap<String, String>>`:
- When `command` is set, the PTY runs `$SHELL -lc <command>` (`cmd /C` on Windows) instead of an interactive shell.
- The `on_output` channel gets a final `Exit { code: Option<i32> }` message, sent for every session, so that EOF and exit stop being the same signal.
- `env` is merged after the existing auth-variable stripping. It can only add `GITWAND_WORKTREE_*` and `GITWAND_REPO_ROOT` (an allow-list), so it can never bring back a stripped secret.

### 10.3 Dev-server

- New routes for every command in 10.1, using `execFile` / `spawn` with argument arrays.
- `/api/git-worktree-add` and `/api/git-worktree-remove` are rewritten the same way, in the same PR, to stop using shell interpolation.
- Merge-back stays partly desktop-only. `worktree_merge_back_prepare` gets a route; the merge and rebase already have one.

## 11. Non-goals

- **v3.16.0:**
  - agent picker;
  - live agent status;
  - in-app permission requests;
  - the sortable worktrees view, which replaces the modal;
  - one WIP row per worktree in the Git Tree;
  - recognizing agent sessions by process instead of by `.claude/`;
  - cross-worktree conflict prediction;
  - cleanup by merged PR or by disk use.
- **Port ranges per worktree** (Conductor): the repo's `setup` script owns that, as Dendreo's does.
- **Migrating existing `gitwand-scratch-*` worktrees** to the new directory: they keep working where they are.
- **YAML `.gitwandrc`.**
- **Running hooks for worktrees GitWand does not own.**

## 12. Delivery

The work is split into PRs, each one shippable and testable on its own:

1. **Config and trust:**
   - the `worktree` schema in `packages/core/src/config.ts`, with its tests;
   - the `.worktreeinclude` reader;
   - the trust store and its dialog.
2. **Terminal:** the `command` / `env` / exit code changes (10.2), Windows Job Objects, stopping by session id, the cwd sweep (§8), and the dev-server mirror.
3. **Worktree service:**
   - the creation part: `worktree_create`, base resolution, include, the record, the setup tab, `url`;
   - both creation paths moved onto it;
   - the dev-server worktree routes rewritten.
4. **Removal:** guards, the removal sequence (§7.2), worktree metadata on snapshots, every removal path moved onto it.
5. **Merge-back:** per-checkout `useApplyFromPreview`, `worktree_merge_back_prepare`, the three modes, and the new merge-back dialog.
6. **Restore as a new worktree.**

Every user-facing string lands in all 5 locales in the same PR.

**Tests** use real git repos (`AGENTS.md`). Required cases:
- base resolution offline;
- an include entry that is tracked, missing, or points outside the repo;
- placeholder quoting with a path containing spaces and quotes;
- teardown with a non-zero exit blocks removal;
- locked and `.worktree-keep` worktrees refused;
- a process left with its cwd in the worktree blocks removal;
- merge-back after `main` moved (merge and rebase), with a conflict the engine resolves and one it does not;
- squash mode is unchanged;
- restore-as-worktree round trip.

**Parity:** the new deterministic read commands (`worktree_resolve_base`, `worktree_guard`) get parity probe coverage.

**Manual QA on Dendreo**, with its real `bin/worktree` as `setup` / `teardown` / `url`:
1. Create a task.
2. Let `main` move on.
3. Merge back in each of the three modes.
4. Remove the worktree.
5. Check that no container, volume or database is left behind.
