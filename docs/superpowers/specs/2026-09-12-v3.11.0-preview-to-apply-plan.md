# v3.11.0 Merge preview-to-apply: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: use `superpowers:subagent-driven-development`
> (recommended) or `superpowers:executing-plans` to implement this plan task by task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Status: all 14 implementation lots complete, 2026-09-14, merged untagged (PR #194). The release close-out is NOT done and is deliberately reopened below.**
v3.11.0 now ships this half plus four more lots (forge-side auto-merge, the dev-server route drift
audit, the history-aware LLM fallback, Finder-like folder navigation), so the
version bump, the CHANGELOG heading, the website changelog entry and the tag all wait for those.
The engine work of this plan is written up under `## [Unreleased]` in `CHANGELOG.md` in the meantime.
Three lots that were in the v3.11.0 entry moved to the roadmap's Later (unscheduled) section instead:
libgit2 stage/unstage (measured 2026-09-14 and declined: a flat ~15 ms win against an index written
without external clean filters, so LFS content lands raw), libgit2 blame (blocked on a
git-version-dependent attribution divergence) and the Linux inotify measurement (needs real Linux
hardware). None can be completed on demand, so none of them holds the tag.

One deliberate deviation from the written plan: the real-repository apply test specified as
`composables/__tests__/applyFromPreview.git.test.ts` lives instead at
`tests/parity/apply-from-preview.test.mjs`, because it drives the orchestrator against the
dev-server's own HTTP routes and therefore belongs with the suites that need a running server.

**Goal:** close the loop between the Conflict Predictor and execution. Apply the engine's
resolutions straight from the preview, let the user hold hunks back (per hunk, or globally by
confidence), and make the two text-editing surfaces real editors instead of a textarea and a
read-only table.

**Architecture:** the apply is frontend orchestration, not a new backend capability. The preview is
a side-effect-free simulation, so applying means running the *real* git operation and re-running the
engine against its actual output, then stopping on the residual. The confidence bar is a new numeric
option in `packages/core`, ANDed with the existing label gate so it can only ever subtract from the
applied set. Per-hunk opt-out is desktop state keyed on the positional conflict index. In parallel,
the CodeMirror wiring currently inlined in `FileExplorerPanel.vue` becomes a three-layer extraction
consumed by the merge editor and the diff viewer.

**Tech stack:** Rust (Tauri 2, `git2`), Vue 3 Composition API, TypeScript, CodeMirror 6, Vitest,
Node dev-server (`dev-server.mjs`).

**Design:** `docs/superpowers/specs/2026-09-12-v3.11.0-preview-to-apply-design.md`
**Roadmap:** `ROADMAP.md`, section `### v3.11.0 - Merge preview-to-apply + editable diff`

  *dependency* line is fine; changing the package's own *version* is not. No task here bumps one.

  needed is already installed.

## T0 - De-risking spike (about 1 hour, no PR)

Two cheap unknowns that block work downstream. Answer both before starting B1 or B4.

- [x] **(a) Does `EditorView` mount in this repo's jsdom under Vitest?** **ANSWERED: yes, with no
  shim.** Probed directly against the repo's own Vitest config. `Range.prototype.getClientRects` is
  **`undefined`** here (not an empty stub), yet CodeMirror degrades gracefully for everything except
  one call. Measured boundary:

  | Capability | Result |
  |---|---|
  | Mount into a host, doc round trip via `dispatch` | works |
  | `state.facet(EditorView.editable)` | works |
  | `.cm-editor` and `.cm-gutters` rendered into the DOM | works |
  | `Compartment.reconfigure` (the theme swap) | works |
  | `updateListener` fires exactly once per `docChanged` | works |
  | `destroy()` empties the host | works |
  | `posAtCoords`, `scrollIntoView` | work |
  | **`coordsAtPos`** | **throws** `textRange(...).getClientRects is not a function` |

  **Consequence: add nothing to `src/test-setup.ts`.** Every assertion B1 and B2 call for is in the
  working column. Only `coordsAtPos` must be avoided. If a later test genuinely needs it, add
  `Range.prototype.getClientRects = () => []` in a **local** `apps/desktop/src/test-utils/`
  helper imported by that file alone, **never** in `src/test-setup.ts`, which runs for all 133 test
  files including node-env ones and must not touch `document`.
- [x] **(b) Is `RepoOperationState.operationHead` the replayed commit (`REBASE_HEAD`) or the branch
  tip?** **ANSWERED: it is the replayed commit.** `read.rs:1109` and `:1131` read it from
  `.git/REBASE_HEAD`. Verified empirically against real git on both halt kinds:

  | Halt kind | `REBASE_HEAD` (= `operationHead`) | `HEAD` |
  |---|---|---|
  | `edit` stop, base moved so the commit was genuinely rewritten | the **original** pre-rebase hash | the **new** rewritten commit |
  | conflict stop | the **original** pre-rebase hash | the **parent**, commit not yet created |

  **Consequences for B4:**
  1. `getPendingSplitForHash(operationHead)` matches `pendingSplits` correctly, because both speak
     the original pre-rebase hash. **No new `RepoOperationState` field, no Rust change, B4 is not
     deferred.**
  2. The conflict row **confirms the correctness trap** the design predicted: at a conflict halt
     HEAD is the parent, so a split button there would `reset --mixed HEAD^` one commit too early.
     Gating on `!hasConflict` is necessary, not defensive.
  3. **A pre-existing latent bug was found, and B4 must not copy it.** See below.

Record both answers in the PR body of the first task that depends on them.

### T0(b) follow-on: a pre-existing bug in the shipped split-at-edit-stop flow

`RebaseEditor.handleSplitAtHead` (`RebaseEditor.vue:340-360`) passes `pending.fullHash`, the
**original pre-rebase hash**, to `splitCommit.openFor`, which uses it for
`getGitShow(repoCwd, targetCommit.hash)` (`useSplitCommit.ts:113`) to populate the modal. Meanwhile
`gitSplitCommit` operates on **HEAD** via `reset --mixed HEAD^`.

Whenever the replayed commit was rewritten (rebase onto a moved base, or a commit whose conflict the
user just resolved), those are two different commits: **the modal shows the user the pre-rebase diff
while the split operates on the post-rebase content.** In the common case of a clean replay onto an
unchanged base the two hashes are identical, which is why this has gone unnoticed.

`openFor` does not validate `hash === HEAD`, and its comment at `:98-99` explicitly anticipates the
"rebase edit-stop flow" as a caller that does not carry parents, so nothing catches it downstream.

**B4 must therefore not relocate `handleSplitAtHead` verbatim.** Use `pending` only to *decide
whether to show the button*; pass **HEAD's** hash and message to `openFor`. Fix the existing
`RebaseEditor` call site the same way in the same task, and add a regression test.
