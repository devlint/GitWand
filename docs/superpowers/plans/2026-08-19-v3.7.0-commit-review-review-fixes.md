# TASK 1 — Stop a routine status poll from wiping commit-review findings (#1, CRITICAL)

## Verified evidence

- `apps/desktop/src/composables/useGitRepo.ts:453` — `status.value = await getGitStatus(cwd, …)`
  inside `loadStatus()`: a **brand new object** is assigned to the `status` ref on every refresh.
- `apps/desktop/src/composables/useGitRepo.ts:326-385` — `repoStats` is a `computed()` whose
  every branch `return`s a **fresh object literal**. Vue 3.4+ only notifies subscribers of a
  computed when `hasChanged(new, old)` (i.e. `!Object.is`) is true, so a fresh literal makes
  `repoStats` notify on **every** `status.value` reassignment, regardless of content.
- `apps/desktop/src/App.vue:1369-1386` — `watch(() => [repoFolderPath.value, repoStats.value.staged] as const, …)`.
  Verified in `node_modules/.pnpm/@vue+reactivity@3.5.32/.../reactivity.cjs.js:1888`:
  ```js
  if (deep || forceTrigger || (isMultiSource
      ? newValue.some((v, i) => hasChanged(v, oldValue[i]))
      : hasChanged(newValue, oldValue)))
  ```
  A **single getter returning a fresh array** takes the `hasChanged(newValue, oldValue)` branch,
  which is `!Object.is(arrayA, arrayB)` → **always true**. So the callback fires unconditionally
  whenever the effect re-runs.
- Callback body (`App.vue:1372-1383`) then does, on every 2 s poll tick:
  1. `secretsScanner.scan(cwd, settings.value)` → a full `scanSecrets` IPC (debounce 400 ms
     always elapses between 2 s ticks — `useSecretsScanner.ts:135-140`);
  2. `commitReview.onStagedSetChanged(...)` → `reset(cwd)`, which **wipes `rawFindings`,
     `lastError`, `truncated`** (`useCommitReview.ts:406-413, 692-699`), plus a
     `git diff --cached` IPC via `refreshCoverageForCurrentDiff`.
- Poll cadence confirmed: `useRepoPoller.ts:36` `POLL_INTERVAL = 2_000`, `:150`
  `setInterval(() => void tick(), POLL_INTERVAL)`, and `tick()` calls
  `actions.onStatusChange(cwd)` → `loadStatus` whenever the porcelain snapshot differs
  (`:105-107`). Note `loadStatus` is also called directly from many user actions.

**Net effect matches the live report exactly:** real findings disappear within seconds, no
interaction needed.

## Fix layer decision (recommended, needs confirmation — see §Open decisions O2)

Fix at **both** layers, in this one commit:

1. **Source layer (`repoStats`) — the real fix.** Memoize the stats object so a structurally
   identical recomputation returns the **same reference**, which stops `repoStats` from
   notifying at all on a no-op poll. This benefits **every** consumer, not just this one
   watcher. Verified consumers: `App.vue:1104, 1197, 2517, 3605, 3698, 3807`,
   `RepoSidebar.vue:36`, `AppHeader.vue:57`, `header/BranchSelector.vue:57`,
   `CommitGraph.vue:30`, and `useGitRepo.ts:399` (`canCommit`).
2. **Watcher layer (`App.vue:1369-1386`) — defense in depth.** Convert to Vue's multi-source
   form so each source is compared by its own primitive value.

### Widen the second source, do not narrow it

`repoStats.value.staged` is a **count**. Once the accidental per-poll refire is gone, a change
that keeps the count identical stops firing the watcher: *unstage A + stage B*, or *restage an
already-staged file after editing it*. The count-keyed watcher always had that gap (the
original plan already documents it: `App.vue:1183-1186`, "scenario (B) editing and restaging a
file that was already reviewed doesn't change the staged file COUNT, so a count-keyed
staged-set watcher never re-fires"), and `proceedToCommit` already compensates for commit
review by recomputing coverage fresh at commit time. The accidental refire was masking it.

So this task **widens** the trigger while making it honest: add a **staged fingerprint** — a
primitive string, safe to watch — and key the watcher on that instead of the bare count. That
strictly covers *unstage A + stage B*, which the count never did. The remaining gap
(same-file content restage) is handled by tasks 2 and 6.

# TASK 2 — Rescan for secrets at commit time (fallout of task 1)

## Why this exists

Not one of the 13 findings: surfaced while verifying #1. Before task 1, the mis-firing watcher
accidentally re-ran `scanSecrets` **every 2 s**, so a secret introduced by editing and restaging
an already-staged file was caught within seconds. After task 1 the trigger is honest, and that
case (staged count *and* staged fingerprint unchanged, content different) is no longer rescanned.
Verified that nothing compensates: `handleCommitRequest` (`App.vue:1140-1152`) reads
`secretsScanner.activeFindings.value` — the **last** scan's result — and never rescans. Commit
review already compensates for the same gap (`proceedToCommit` recomputes coverage fresh,
`App.vue:1207-1210`); the secrets gate does not.

This is security-relevant, so it must not be left as an implicit regression. **Flagged as open
decision O1** — implement as planned, or explicitly accept the gap.

## Files

- **Modify `apps/desktop/src/composables/useSecretsScanner.ts`:** expose the already-existing
  `runScan` as `scanNow(cwd, settings): Promise<void>` (awaitable, un-debounced). It is
  already internally non-throwing (`:120-134`, "a scan failure must never disrupt the commit
  flow"), so the commit path can `await` it safely. Add it to `UseSecretsScannerResult` with a
  doc comment stating it exists for the pre-commit gate specifically.
- **Modify `apps/desktop/src/App.vue` `handleCommitRequest` (`:1140`):** `await
  secretsScanner.scanNow(repoFolderPath.value ?? "", settings.value)` **before** reading
  `activeFindings`. Cost note in a comment: this is one IPC on the commit path, consistent with
  the two `proceedToCommit` already awaits (`git rev-parse HEAD`, `git diff --cached`).
  Session dismissals are preserved because `activeFindings` filters by `dismissedKeys`
  (`:73-75`), which `runScan` never touches.

# TASK 4 — The commit gate re-prompts on a live unresolved risk finding (#2)

## Verified evidence

`apps/desktop/src/composables/commitReviewState.ts:328-338`:
```ts
export function resolveCommitReviewGate(input: {
  enabled: boolean; staged: number; decision: ReviewDecision | null; iterations: number;
}): CommitReviewGateAction {
  if (!input.enabled || input.staged <= 0) return "proceed";
  if (input.decision !== null) return "proceed";
  if (input.iterations > 0) return "proceed";
  return "prompt";
}
```
Nothing consults the findings. Combined with #1 (findings wiped), a commit can silently carry
`GitWand-Review: ran (iter:N, coverage:100%)` while a real Risk finding was flagged and never
seen. Verified caller: `App.vue:1195-1205`.

Consistency check against **D8**: additive. Cancelling still cancels the commit; skipping still
requires an explicit click. Consistency check against "never a hard stop": preserved, the modal
always offers Vouch and Skip, both of which proceed. No infinite loop: once the user clicks
Vouch/Skip, `decision !== null` short-circuits first.

"Live and undismissed" is exactly `commitReview.findings` — the already-filtered list
(threshold + cap + dismissed classes, `useCommitReview.ts:365-371`).

## Files

- **`apps/desktop/src/composables/commitReviewState.ts`** — add a **required** field
  `unresolvedRiskCount: number` to `resolveCommitReviewGate`'s input (required, not optional,
  so no call site silently keeps the old behavior), and insert the branch **after** the
  decision check and **before** the iterations check:
  ```ts
  if (!input.enabled || input.staged <= 0) return "proceed";
  if (input.decision !== null) return "proceed";
  // A live, undismissed risk-severity finding always earns one explicit
  // decision, even when a review already ran this cycle: otherwise the commit
  // records "ran" for a risk the user may never have looked at. Still not a
  // hard stop (Vouch and Skip both proceed), and dismissing the finding
  // removes it from `findings`, so it stops re-prompting.
  if (input.unresolvedRiskCount > 0) return "prompt";
  ```

  Update the function's doc comment (`:311-327`) to list the new branch in the same bullet style.
- **`apps/desktop/src/App.vue:1195`** — pass

  Extract that expression into a `commitReviewUnresolvedRisks` computed next to
  `repoSidebarProps` so task 5's modal props reuse it rather than recomputing.

# TASK 10 — `parseFileDiff` no longer emits a phantom trailing context line (#10)

## Verified evidence

`apps/desktop/src/utils/unifiedDiff.ts:41-44` asserts as intentional:
> "a bare empty string is also treated as a (whitespace-stripped) context line, never as a
> phantom add/delete"

and `:49` iterates `rawFileSlice.split("\n")`, with `:80-81` classifying `line === ""` as a
context line that increments **both** `oldLine` and `newLine`. A raw `git diff` always ends with
`"\n"`, and `indexDiffFiles` (`:24-26`) joins its collected lines with `"\n"`, so the **last**
file's slice ends with `"\n"` → `split("\n")` yields a trailing `""` element → one phantom

what the hunk header declared. Intermediate files are unaffected (their slice ends right before
the next `diff --git`).

This is **pre-existing**, not introduced by this PR: `unifiedDiff.ts` was lifted verbatim from
`usePrPanel.ts` (its own header, `:4-13`), and `usePrPanel.ts:39,46` now imports and re-exports

parser's explicit prior fix for the identical bug class:
`apps/desktop/src-tauri/src/commands/read.rs:1192-1198` —
> "Empty strings (from split on blank separator lines or trailing EOF newline) must NOT be
> classified as context. Doing so adds a phantom zero-length context line to the hunk, which

```ts
const lines = rawFileSlice.split("\n");

// element that is not a diff line at all. Dropping exactly that element (and
// only when it is last) keeps a genuine blank context line mid-hunk intact,

if (lines.length > 0 && lines[lines.length - 1] === "") lines.pop();
```

# Deferred (with reasoning)

## #13c — stale repo tabs spam failing git calls: **deferred, not patched here**

**Verified facts:** `useRepoPoller.ts:150` runs one consolidated `setInterval` at
`POLL_INTERVAL = 2_000` (`:36`); each tick runs `gitExec(cwd, ["status","--porcelain","--branch"])`
and `return`s silently on `exitCode !== 0` (`:100-122`), with a bare `catch {}` for spawn-level
failures. Only the **active** tab is polled (`App.vue` drives `setFolderPath` from
`useRepoTabs.activeRepoPath`, `useRepoTabs.ts:147-155`), so the noise is bounded to one repo.
Tabs are hydrated from localStorage at module load with **no** existence check
(`useRepoTabs.ts:100-105`), so an active tab pointing at a deleted temp dir fails forever.

**Why not a quick patch:** the only cheap trigger available is "the porcelain probe failed",
which cannot distinguish a deleted directory from a legitimate transient failure
(`index.lock` during a rebase, a locked ref, a slow network filesystem). Suspending the poll on
generic failures would freeze status updates during exactly the long-running git operations
where live status matters most: a worse bug than log noise. Doing it properly needs either a
directory-existence signal (a new IPC, which this fix round forbids) or a per-backend error
taxonomy, plus a real "this repo is gone" UI state on the tab and a recovery path. That is a
feature, not a fix.

**Recommendation:** file it as a roadmap follow-up ("detect a vanished repo path, stop polling
it, surface a tab error state with a Close/Relocate action"). If the reviewer prefers a stopgap
now, the smallest defensible one is a 3-consecutive-failure suspend with resume on
`setFolderPath` **or** any manual refresh, plus a visible error banner so the suspension is
never silent. See open decision **O6**.

## `PullRequestPanel.vue`'s private diff parser: **noted, not touched**

`PullRequestPanel.vue:153-199` holds its own copy of `parseUnifiedDiff`, byte-identical in the
relevant branch (`:193` `line.startsWith(" ") || line === ""`), so it carries the same phantom
trailing context line that task 10 fixes in `utils/unifiedDiff.ts`. Deleting the duplicate in
favor of the shared util is the right end state but is a separate refactor with its own
regression surface (this component renders the PR diff for every forge). Task 10 deliberately
leaves it alone; log it as a follow-up so the duplication does not become permanent.
