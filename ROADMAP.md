_Two tracks (decided 2026-11-26). **3.x**: finish what is in progress, then fixes only — no new feature, and fix only what v4.0 will not rewrite; lots are cut by area so they can run in parallel worktrees. **v4**: starts now, with the map of the app from top to bottom, then the new environment. Proposed mechanics, to confirm: one repository and one `main`, no long-lived v4 branch — the new workspace is a second frontend entry in `apps/desktop`, loaded as a lazy chunk behind a setting, on the same Rust commands and `packages/core`; a fix to shared code then serves both, 3.x builds carry the preview, and the 3.x main bundle does not grow._

_Direction for 4.x (2026-11-26): GitWand becomes the place where agent work becomes mergeable. Code is more and more written by agents, several at a time; the bottleneck moves from writing to integrating and verifying. Launching agents and showing their status is table stakes that agent CLIs will absorb. What holds: integration as the unit of work (predict, order, resolve what is certain, show a human only what needs judgment), agents as users (`@gitwand/mcp` and the CLI are first-class products, with their own goals in every release), measured trust (benchmark, per-pattern accuracy, open dataset), and attention as the scarce resource ("read these 40 lines", with the proof). The demo that sums it up: five agents on five worktrees, four integrated without a question, the one real conflict shown, two silent conflicts flagged that git would not have seen. v4 is a break, not an evolution (decided 2026-11-26): GitWand becomes the one environment the work happens in, and its job there is to **supervise and control CLI agents**. Today the maintainer works in an agent workspace and leaves it for GitWand; an integration view opened only at merge time comes too late to predict anything. The model: the sidebar is the list of tasks (one worktree each, every repository, the one waiting for an answer on top) and is always there; the main panel follows the selected task in three modes — **Session** (the agent's terminal), **Files** (the existing File Explorer, editor and diff, scoped to the task's changes), **Integration** (the merge flow, with the proof); **Integrate** is the view across tasks. The classic repository features are not a destination any more: they become **instruments of control and visualization** inside the environment (graph, restore points, guardrails, PR & CI), and the occasional ones (stash, tags, submodules, bisect, release notes) move to the command palette. Control is exercised first at the Git boundary — worktree, hooks, commit review, push — because every agent ends up there whatever its CLI; richer control comes per CLI where it exposes hooks. No new editor features: the agent writes, the existing editor is for the small fix. Someone who commits by hand loses nothing: their work is a task with a human as author. ### v3.15.0 — Ship & harden

**3.15.0 — ship what is ready**

- **Combined Diffs** — merged, unreleased (multi-commit, non-contiguous aggregated diff; detail in CHANGELOG, Unreleased).
- **#315 — the Git Tree skips refs events that change nothing it shows** (`git_refs_fingerprint`). Closes the Git Tree follow-up from #278 (full log reload on every refs event, ≈750 ms on a 74k-commit repo). Known gap, accepted: a ref that moves and comes back between two reads leaves stale decorations until the next ref move or a manual refresh.
- **#314 — hardening batch**: AI endpoint gate (closes the `ai_http_request` `auth: "none"` follow-up from #244), PR/MR bodies on stdin (#234), model-listing timeouts that kill the process tree (#237), `pullAutostash` fixture retry. To check at merge: the #234 case where a background revalidation racing a save briefly shows the old title/body is not in its description. Not tested: Windows, a real `glab`, the native dialog in the packaged app (see the checklist below).
- **#317 — guided bisect** (Gitoryx): start from the Git Tree (two commits, or "from here" to HEAD), Good / Bad / Skip from a banner that also follows a bisect started in a terminal (paths, `--first-parent`, `--no-checkout`, custom terms), remaining commits and steps, culprit or skipped candidates opened in the Git Tree, End bisect (End here when the start branch is gone). QA done in `dev:web` and in the Tauri app (macOS debug build). `git bisect run` moves to v4.4.
- #265: a stale block reason can linger up to one fetch tick (30 s); a branch literally named `HEAD` or `unknown` is treated as detached (the invisible bisect is closed by #317, which reports it in the repo state)
- **Bundle budget** — #317 raises it from 992 to 1,002 KB (main chunk measured at 1,001 KB with #314 and #315 merged: bisect wrappers, strings and Git Tree wiring; the banner is a lazy chunk). The raises these three need are the last ones: from v4.0 a feature lands in a lazy chunk.

**3.15.x — lot A: resolvers** (wrong resolutions a user can see)

- Dockerfile resolver: a one-sided deletion inside a stage comes back (an instruction only on the other side is always kept); all `COMMENT` lines share one key, so a comment can replace another; `mergeStage` emits in ours' order, so a reorder on theirs is lost. All three predate #278
- imports resolver: `oursBySource`/`theirsBySource` keep only the last import per module, so `{ a, X }` + `import type { T }` against `import X` still keeps both and declares `X` twice; `require` bindings are not parsed, so any `require` against an import of the same module is treated as a collision (conservative)

**3.15.x — lot B: test net** (before v4.0 moves code)

- **Test the log view epoch** (follow-up to v3.12.0, #214) — the filter/scope change that drops in-flight log pages and the forced-reload depth (`forcedReloadDepth`) have no test; a `useGitRepo` test for "filter change while a page is in flight" would lock them in.
- `merge_back_without_a_recorded_base_still_works` fails under full-suite load (seen 2026-10-10, not reproduced in 15 runs of the `scratch` tests on 2026-11-26; the `pullAutostash` half of that report is fixed in #314)
- parity-probe dispatch entries for `read_commit_template` and `ai_http_request` (`none` auth against a local fixture server)

**3.15.x — lot C: security & data safety**

- #239 treats a pull later undone by a local reset as a local rewrite (the collaborator's commit was once a local tip), so Force Push is offered and would drop it. The `--force-if-includes` fallback (a force push whose destination tip cannot be read) has the same blind spot: that commit is in the branch's reflog, so git accepts the push. Judging it needs to tell "pulled, then reset away on purpose" from "rewritten". Explicit force pushes are not affected: they show the commits they will overwrite and lease that tip
  - _Re-check first against the force-push fixes already in Unreleased (lease on the tip read at click time, `--force-if-includes` fallback): part of this may be closed._
- Copilot is unverified (not installed when the follow-ups were written): its run directory, stdin support and lockdown; Antigravity (`agy` 1.0.13) still gets the prompt on argv, and its tools are not restricted
- the user's own MCP servers still load for Codex and opencode (no confirmed switch: `-c 'mcp_servers={}'` does not remove them)
- Windows: a grandchild of the `claude --help` probe can outlive it once the direct child has exited (needs a Job Object)
- the `ai-runs` sweep (24 h, at base setup) could remove a run directory still in use by a run older than that in another GitWand process
- `img-src` stays `https: http:` for self-hosted forge avatars — proxy or allowlist avatar hosts, then tighten it
- `ai_http_request` under `pnpm dev:web` goes to any origin unasked: the dev server has no native dialog to mirror `check_open_endpoint_with` (from #314)
- allowed AI endpoints cannot be listed or revoked from Settings (they live in the keychain, service `gitwand:ai`, one account `open-endpoint:<SHA-256 of the origin>` per origin); a refusal lasts until restart or an explicit Test connection / Refresh (from #314)
- an OpenAI-compatible server without a key: the model list loads (`auth: "none"`), but `isAvailable` requires a key and `callOpenAICompat` always sends `bearer`, so completions are never offered. Support it end to end or say so in Settings (from #314)

### Performance & baselines — v4 track (was v3.16.0)

_Moved to the v4 track on 2026-11-26, since 3.x takes fixes only. The measurements run against 3.x as it is and give the floor the new environment must hold; the changes land in the v4 work (the in-process git reads are backend and serve both; the diff views and highlighting are rebuilt with the new Files mode rather than patched twice). Already in place: vendored `git2` (diff, directory listing), Tauri Channels for streamed results, `@tanstack/vue-virtual` on the commit log and the file tree, a watcher that coalesces events and skips build folders, and the refs fingerprint of #315. What follows is what is left._

**Measure first**

- **Linux inotify validation** (moved out of v3.11.0, 2026-09-14, same reason): the v3.10 watcher registers inotify watches across the working tree, and registration cost on a `node_modules`-sized checkout was never measured on real Linux hardware, the work having been done on macOS where FSEvents has a different cost model. It is a measurement, not a change: the outcome may be "nothing to do" or "the watcher needs rework", which is precisely why it cannot sit on a release's critical path. Needs doing before the watcher is leaned on any harder, and before the v4.3 indexer becomes its second consumer.
- **Snapshot cost on very large working trees** — each snapshot runs `git add -A` into a scratch index, which is O(worktree) on a cold cache. Fine on normal repos, unmeasured on a 100k-file monorepo. Benchmark alongside the v3.10 FS-watcher work, where the same walk gains a second consumer.

**Git reads in-process**

- **libgit2 phases 3-4** — migrate `git_log`/`git_show` (revwalk, the real win on 40k commits — but the object-fetch loop needs optimizing first) then `git_file_log` (`--follow`/rename tracking to reimplement). Scheduled here; `gix` is evaluated in the spike below.
- **`gix` spike, time-boxed** — same scope as phase 3 (revwalk for `git_log`/`git_show`), same parity tests, same benchmark repo; one decision at the end: stay on `git2` or move the reads to `gix`. Writes, filters, hooks and credentials stay on the CLI either way.
- **SHA-256 / reftable repositories** (2026-10-08 scan: GitButler 0.19.10, Sublime Merge 2130, Zed) — git handles them, but a few GitWand parsers assume 40-hex ids (`git/libgit2.rs:754`, `dev-server.mjs:4165`). Audit every such assumption and add a SHA-256 fixture repo to the parity tests.
- **Git Tree: reload only the first page on a refs change** (follow-up of #315) — a refs event whose refs did change still forces a full log reload and restarts the background prefetch (≈750 ms of `git log` on a 74k-commit repo), even when only rows of the first page moved. Reloading only the first page needs to know where new commits land in the held log (a fetched branch with old commit dates is inserted deep).

**Rendering**

- **Virtualize the diff views** — `useVirtualRows` covers `CommitLog`, `FileTreePane` and `PrInlineDiff`; `DiffViewer`, `CommitDiffViewer` and `CombinedDiffBody` render every line of a diff.
- **Syntax highlighting off the main thread** — highlight.js runs on the main thread and its eager language set sits in the main bundle (`utils/highlight.ts`). Move it to a Web Worker (or to Rust), highlight the visible window only; this also gives bundle budget back.
- **IPC payloads** — audit the `invoke()` calls that still return a whole log or a whole diff as one JSON; stream them over a Channel in pages, visible window plus a small buffer.

**Baselines**

- Publish the numbers next to the engine benchmark: cold start, first log page and full prefetch on the 74k-commit repo, a 50,000-line diff, status on a large working tree, watcher cost on Linux. v4.0 is checked against them, like the bundle budget (`apps/desktop/perf/`).

_Checks that need another machine, another person or the packaged app. Run when the machine or the reporter is available; a release does not wait for them._

- Issue creation (#301) and private-repository attachments (#302) were tried under `dev:web` only: check them in the packaged app
- **Manual pass over the AI hunk queue in the packaged app** (outstanding from the issue #196 work). The UI half is done: a run against the real `claude` CLI under `pnpm dev:web` (4 complex hunks, one file) watched the batch stage 4 answers, confirmed one hunk and saw the other 3 survive renumbered onto the right hunks, saw a rerun re-buy nothing, and saw a cancelled call's late answer land nowhere. What is left is the responsiveness half, and it **cannot be checked under `dev:web`**: `dev-server.mjs` spawns the provider with `spawnSync`, so it blocks its own single thread for the whole call (measured: an unrelated API request waited 10.1s; the 4-hunk batch took 79s as four serialized calls, never 3 concurrent). The dev-server therefore shows the opposite of what the Rust `spawn_blocking` change fixes. The mechanism itself is now pinned by a Rust regression test (`commands::ai::tests`): three AI commands are put in flight on a deliberately single-worker runtime and a 50ms timer still fires in 50ms, where the same test measured 3.2s before the `spawn_blocking` change. What is left is therefore only the human half, in the packaged app: that the window keeps painting and the progress and partial-failure lines read correctly while a real batch runs.

- #263: the fr/es/pt-BR/zh-CN strings for the Keep mode were not read by a native speaker

### v4.0.0 — The workspace (a break)

_A new working environment, not a rearranged one: GitWand supervises and controls agents that run in their CLI. It is built on the map of the app (106 Vue components, 354 Tauri commands in 33 Rust modules, a main bundle at its budget, several things that exist more than once), and it is the one release where removals and breaking changes are allowed. Developed as preview builds while 3.x only takes fixes; its largest risk is the terminal, which becomes the main surface and has to hold up all day (rendering, shortcuts, several sessions, recovery after a freeze)._

**The environment**

- **Task sidebar, always there** — one row per task (a worktree and its branch), across repositories, grouped by repository; on top, what waits for an answer. Each row: agent or human, status, files changed, PR state, predicted conflict with another task. Replaces the repository tabs, the toolbar and the dock.
- **Three modes for a task** — **Session**: the agent's terminal as the main surface. **Files**: the File Explorer, editor and diff that exist today as an overlay, given a real panel; opens on the task's changed files, with a switch to the whole tree; shows which session wrote a change. **Integration**: the merge flow (completed in v4.1).
- **Repository instruments, not a repository view** — graph (every task's branch against the target), restore points (Time Machine: go back to before this session), guardrails, PR & CI: panels opened beside the task, for control and visualization. Stash, tags, submodules, bisect, release notes, new issue: command palette.
- **The centre is never empty** — there is always a selected task; no "select something" screen.

**Supervise and control agents**

- **Control at the Git boundary first** — works for any CLI, because every agent ends up committing and pushing: worktree lock while an agent runs, lifecycle hooks (v3.13), commit review and secrets scan as gates (v3.7, v3.5), push held until validated, protected branches, restore points before and after a session.
- **Guardrails per task** — what this agent may do without asking: paths it may touch, commands allowed, whether it may commit, whether it may push. Never auto-allow by default; a refusal is structured (principle 6).
- **Stop, pause, resume** a session from the sidebar; a frozen or crashed session is recovered with its history.

**Creation**
- Start from a branch, a remote branch, a PR (`pull/<n>/head`) or a Launchpad issue (GitKraken 12.4): branch named after it, issue body as the starting prompt
- Agent picker (Claude Code, Codex, Gemini, Antigravity, opencode… — the providers GitWand already knows), not Claude Code hard-wired
- **Antigravity CLI (`agy`) as a first-class agent, early** (asked 2026-11-27) — GitWand already launches it in the terminal and uses it as an AI provider; what the workspace needs on top: recognise its sessions and worktrees (`detect_agent_tool`), live status from PTY and process like any CLI, then whatever hook mechanism it exposes for richer states and permission requests. Its two open hardening items are in the 3.15.x security lot (prompt still passed on argv, tools not restricted) and come first

**Visibility**
- A worktrees view, sortable and filterable, replacing the modal: branch, dirty count, ahead/behind, last activity, disk use, PR state, env URL, agent status
- One WIP row per dirty worktree in the Git Tree (GitKraken 12.3), building on the #224 WIP-as-Git-Tree-entry work
- Recognise worktrees created by other tools (`.claude/worktrees/`, Conductor, Superset…) and identify an agent session by its process, not by the presence of a `.claude/` folder — `detect_agent_tool` flags every worktree of a repo that commits `.claude/`, GitWand's own included
- The task sidebar and the Integrate view keep a place for a per-task impact signal, so v4.3 can add "symbol-level impact" without redoing the screens

**Agent status**
- **Live status** — per session: running, waiting for input, idle, exited. Baseline with no integration: PTY output activity + process state (works for any CLI); richer states from each CLI's own hook mechanism where it has one, starting with Claude Code hooks. Shown on terminal tabs, in the worktrees view and as an OS notification when a background agent starts waiting
- **Permission requests in-app** — when the CLI exposes it (Claude Code hooks first), surface the pending tool call with the exact command, Allow / Deny from the panel. Never auto-allow; an unanswered request stays pending in the terminal exactly as without GitWand

**Cleanup**
- `git worktree lock` while an agent runs (Claude Code does the same), unlock when it exits
- Clean up once the PR is merged (v3.14 merged-PR detection, `gh_branch_pr` as the signal) or after N days inactive, single or batch (Dendreo's `clean --merged`), always through `teardown`

**Follow-ups from v3.13.0**

- Restore as worktree opens a tab on the restored worktree (a toast only today); removed worktrees leave the Recent list
- The worktree manager shows "No worktree" for a moment while it loads; the apply button keeps "Merge and auto-resolve" in Rebase mode

**The map (how it gets built)**

- **Inventory by domain** (repository & status, history & Git Tree, diff, merge & resolution, forges & PRs, AI, worktrees & agents, terminal, settings): for each, its views, composables, Tauri commands, dev-server routes, weight in the bundle and how it is tested (unit, parity, `dev:web`, packaged app). Kept in the repo and updated like the command registry.
- **Use it as the rule for new work** — a feature names the domain it belongs to before it is built; one that fits none is a decision, not an addition.
- **How each domain is tested** — two PRs in a row (#314, #315) were verified under `dev:web` only, and `dev-server.mjs` behaves differently from the Rust side in places (`spawnSync` for AI calls, CRLF in diffs). The map states, per domain, what `dev:web` can and cannot prove.

**Regroup**

- **Views are re-homed before they are redesigned** — each existing view is lodged in the new environment by domain; the mockups decide the frame, the map decides where each piece goes.
- **One surface per flow, as a rule** — a flow that today crosses several modals is a candidate for one screen that advances by steps. First application in v4.1 (merge).
- **One lazy chunk per domain** — the main bundle keeps the shell and the repository view; every other domain loads when it is opened. Target: a main-bundle budget that goes down, then stops moving.
- **Design: one button system** (2026-11-24, from the v3.14 GitHub QA) — `assets/main.css` has a global `.btn` (`--primary`, `--secondary`, `--ghost`, `--danger`, `--success`, `--icon`, `--sm`, `--xs`, `--lg`, `--ai`), used in ~70 components, yet ~119 component-local button classes (`.xxx__btn`, `.xxx-btn`, `.bm-btn`, `.eco-btn`…) restyle buttons on their own. Each one re-decides padding, radius, hover and disabled states, and they drift: the stack banner's primary button lost its accent on hover because a local `:hover` outranked the local modifier (fixed by moving it to `.btn`). Inventory the local classes, map each to a `.btn` variant or justify a new one (dense rows, toolbar segments, BaseModal's `.bm-btn` and its specificity rule in AGENTS.md), then migrate in batches with a before/after screenshot per batch, light and dark.
- **Per-project identity everywhere** (from the #246 review) — the project's identity (`commitIdentityFor`) reaches plain commits and custom automations only; amend, split, `--no-ff` merge, revert and cherry-pick still use git's config, so the committer (and for merge/revert/cherry-pick the author) can differ inside one project. Route every commit-creating command through it. Also key `identityOverrideByRepo` on a canonical path (case-folded on case-insensitive filesystems, worktrees resolved to their main repo), so the same project opened through another spelling or a linked worktree keeps its identity
- **One diff parser, one place that derives file status** — closes the four #269–#270 follow-ups below instead of patching each copy:
  - CRLF: Rust strips `\r` from diff line content, the dev-server keeps it (also true of `git_diff`)
  - file status (added/deleted/renamed) is still derived in several places with different coverage (`parse_diff_hunks`, `parse_multi_file_diff`, `devParseDiffHunks`, the dev-server `git-show` loop)
  - combined `@@@` hunk header numbers differ (Rust old 1,1 / new 0,1; core and the dev-server 0,1,0,1), and `isPureMove` on a combined hunk
  - strict hunk counts cut a hunk whose header undercounts its body; no forge path in the app sends such diffs today

**Remove (breaking)**

- **Decide the fate of the `explainOnly` option** (follow-up to the v3.7.2 predictor fix): it short-circuits `resolveHunk()` before the format-aware dispatch and the confidence gate, so any caller that reads `stats.autoResolved` after using it gets a structural `0`. That is exactly how `gitwand preview` and two MCP tools shipped broken. After the fix the option has zero consumers in the monorepo while staying part of the public `GitWandOptions` contract, so it is now a footgun with no user. Either remove it (breaking change for external consumers, if any) or redefine it as "classify and resolve, but do not assemble merged content", which is what every call site actually wanted.
- **Retire the frontend's "default to GitHub" forge fallback** (follow-up to the v3.7.3 self-hosted-GitLab fix, #168): `useForge.ts`'s `getProviderByUrl`/`usePrPanel.ts`'s pre-resolution `forge` computed still assume `githubProvider` whenever detection hasn't resolved yet (no remote, `dev:web` mode, or a genuinely unrecognized forge) — a deliberate, documented backward-compat default, not an oversight. The Rust-side detection is now forge-agnostic end to end (URL match → `glab`/`gh auth status --hostname` probe), so the one remaining non-deterministic step is this UI default. Precedent exists for the alternative: Cursor Origin (#165) shows an honest "unsupported forge" state instead of guessing. Doing the same here would need the brief pre-resolution window (before `gitRemoteInfo()` returns) to render a neutral/loading state instead of an optimistic GitHub guess — deferred until there's a concrete report of it mattering, since today it never surfaces the wrong forge for supported CLIs.
- **libgit2 for `list_repo_tree`** (candidate, 2026-10-01) — the File Explorer panel's one-shot tree is `git ls-files --cached --others --exclude-standard`, capped at 20,000 entries. It could read the index directly and classify untracked entries with `is_path_ignored`, the way v3.11.2's `list_repo_dir` does (66 ms for a 6,000-entry directory against 1.6 s with `git check-ignore`). Decision for v4.0: retire `list_repo_tree` (no frontend caller since v3.11.2, when the panel moved onto `useLazyRepoTree`) or migrate it to libgit2 if a caller returns. Same rule as every libgit2 migration: measure first, keep the CLI fallback, cover it with parity tests. libgit2 stays off anything that runs filters, hooks or external config (LFS, signing, credentials), off writes, and off algorithms it implements differently (blame, histogram/patience diffs).

**Security, structural**

- an XSS in the webview still drives every IPC command: scope commands per window/capability, and give `read_file`/`write_file` a registry of repositories the user opened rather than the `.git`-ancestor check (a dotfiles repo at `$HOME` passes it)

### v4.1.0 — Resolution engine

_The engine's principles written down, then the loop that lets real use correct it. Starting points: `core-analyse.md` (2026-04: too textual, naive `whitespace_only`, discrete confidence, no post-resolution validation) and the measured accuracy of v3.9._

**Principles and research**

- **A written position for the engine** — what it guarantees (deterministic, explainable, never silently applies a `complex` hunk), what it refuses to do, how confidence is defined and measured, and where it stands against the research on structured and semantic merge. Published in `docs/` and on the website; every resolver is then checked against it.
- **Review `core-analyse.md` against today's code** — which of its weaknesses v3.9 to v3.12 closed, which remain, and which become v4.3 work (symbol level).

**The journal and what it feeds**

- **Journal of resolutions** (deferred from #301 part 3): a bad resolution found after the file is saved (tests failing after the merge) cannot be reported from GitWand, since nothing keeps the hunk, its versions or the engine's reasoning once the merge editor closes. A journal of applied resolutions would let "Report a bad resolution" work after the fact, and from bulk "resolve everything" runs that are never looked at hunk by hunk.
- **Local accuracy screen** — "engine accuracy on this machine", read from the journal: per pattern and per language, how many resolutions were accepted, edited after apply, rejected or undone. Useful with nothing shared, and it is the same store as the Code Intelligence feedback loop (v4.3) and `useResolutionMemory`.
- **Opt-in shared counters** — the only automatic channel, and off until the user turns it on:
  - asked once the screen above has numbers to show (around twenty resolutions), never at launch, with the exact payload displayed before the choice
  - what is sent: weekly aggregated counts keyed by conflict type, resolver, confidence bucket, language, engine version and outcome
  - what is never sent: file content, paths, repository names, hashes of lines, an installation identifier
  - the collection endpoint stores no IP address; legal review (GDPR) before it ships
  - a `.gitwandrc` key turns the question off for a repository or a team
  - the aggregated dataset is published, next to the benchmark
  - reading the data: "accepted" is not "correct"; edited, rejected and undone are the reliable signals
- **Cases stay explicit, one by one** — a hunk is code and cannot be anonymized. Learning from a case goes through "Report a bad resolution" (#301), with a preview of what is sent, made possible after the fact by the journal. An optional skeleton form (identifiers and literals replaced by tokens) still shows structure, so it belongs to this channel only.

**One merge surface**

- **The merge flow on one screen** — today it crosses at least seven components (`MergePreviewPanel`, `ResolutionPreviewPanel`, `MergeEditor`, `MergeApplyReport`, `ResolveAutoSummaryModal`, `MergeBackDialog`, `MergeSuccessModal`). One surface that advances by steps: preview, what was resolved and why, what needs a decision, apply, report.
- **The proof next to the decision** — every automatic resolution shows its pattern, its confidence and the measured accuracy of that pattern; the screen says how many lines are left for a human to read.
- **Same state for agents** — the screen renders a structured state that `@gitwand/mcp` exposes as is.

**Context and queue**

- **Rebase preview loses commit provenance** (deferred from v3.11.0 lot A1): `preview_rebase` replays each commit of the stack separately, then deduplicates the results per file keeping the strongest conflict signal (`read.rs`, the `by_file` fold). Which replayed commit actually produced a given conflict is discarded in that fold, so the panel cannot say "this conflicts at commit 3 of 5", and a future per-commit "stop here" apply cannot be driven from the payload. Fixing it means a new field on the serialized `FileMergePreview`, which ripples into the dev-server route and the parity normalization, so it was left out of the release that added the routes. The scratch-file race and the missing `-L` labels in the same function were fixed; this one is purely an enrichment.
- **History-aware prompts for the MCP** — align `buildResolveHunkPrompt` / `gitwand_resolve_hunk_llm` with the v3.11.1 history context (`collectHunkHistory` is already exported from `@gitwand/core`).
- **Rename-aware history** — `blame -M -C` / `log --follow` for the v3.11.1 history context.
- **Honor `.gitwandrc` `llmFallback.model` / `maxTokens` on the desktop** — ignored today in favour of the app's AI settings.
- **Hard cancel for an in-flight AI call** (deferred from the issue #196 work): cancelling a hunk or a batch marks the entries idle and discards late results, but an already-spawned `claude -p` keeps running to completion. Killing it needs a Rust command holding the process handle plus a way to address it from the frontend, which is its own piece of work.

### v4.3.0 — Code Intelligence: code-graph impact before merge

_Renamed from "Blast Radius" on 2026-11-26: the release builds a layer (import graph, reverse dependencies, co-change, test mapping) that serves the Impact panel, silent-conflict detection, review ordering and the cross-worktree prediction of v4.2, so it is named after the layer, not after one of its outputs. "Code Intelligence", not "Intelligence": the layer is deterministic and local, with no model in it. "blast radius" stays in the text as the ordinary phrase._

_Inspired by Snipara's project-intelligence layer. Before a merge/rebase, answer: "what does this operation risk breaking?" — the natural extension of Conflict Predictor + `postMergeRisk` (v2.4.1), and a headline differentiator. The same graph also answers the question one step later: "did it actually break something a text merge couldn't see?"_

**Today's baseline** — `packages/core` already embeds tree-sitter (TS/JS/Python/Go/Rust WASM grammars), an ES/CJS import parser (`resolvers/imports.ts`) and parse-tree validation (`validate-parse-tree.ts`), but no dependency graph, caller discovery, or test mapping.

- **Early exit before parsing** — `git diff --name-status` on the two branches first: if every path is either newly added with no `import`/`require` line referencing a symbol the other side changed, or matches an asset/doc extension (`.css`, `.png`, `.md`, …), the engine declares no possible semantic collision and returns without loading tree-sitter. Same spirit as `.gitwandrc`'s `generatedFiles` skip. Cheap, not literally free — an added file's imports still get scanned against the other side's changed-symbol list, since a new file can call into a renamed export it never touched in the diff
- **Import graph** — `packages/core/src/codeanalysis/`: tree-sitter queries build the module adjacency graph (browser-safe, incremental). Cached locally, content-addressed by blob SHA (git's own object model, no external index format): a file's parsed edges are only recomputed when its blob changes, so re-running against an unchanged `main` costs nothing. Considered and dropped: downloading a prebuilt LSIF/SCIP index from CI — real repos rarely have one, and it would pull in exactly the cloud/infra dependency the local-first positioning avoids elsewhere on this page
- **Reverse dependencies** — for each file touched by the operation: who imports it, which exported symbols changed
- **Shallow parsing on dependents** — full AST only for the files a branch actually changed; on unmodified files reached through the reverse-dependency edges, tree-sitter queries pull import declarations and call expressions only, function bodies/loops/local variables are never walked unless the file itself was touched. Keeps the cost proportional to the blast radius, not to the repo
- **Silent conflict detection (`detect_silent_conflict`)** — the case git's text merge never flags because the two sides touched different files: branch A renames a symbol or changes its signature, branch B keeps calling the old shape somewhere the line-level diff never intersects. Runs the same import graph against the merge's actual result (local `git merge --no-commit --no-ff`, zero side effects, same discipline as `gitwand_preview_merge`) instead of the pre-merge diff. A scored pattern registry (`renamed_export_vs_import`, `signature_change_vs_unchanged_call`, `deleted_variable_vs_scoped_reference`) reports a traced collision — `files_involved`, `confidence`, a `trace` built only from real symbol/line names, never a paraphrase — and never auto-fixes it. Mirrors the text engine's own rule (a `complex` hunk is never silently applied, v3.9.0) one layer up, at the symbol level instead of the line level
- **Probable-test detection** — heuristic mapping (`*.test.*` / `*.spec.*` naming + import edges) → "these 12 tests likely cover the changed code"
- **Co-change analysis** — "these files historically change together" mined from local `git log` (zero cloud, cheap); a second impact signal complementing the static import graph, exactly the history hop Greptile does server-side
- **Impact panel** — new tab in `MergePreviewPanel`: impacted files ranked, affected symbols, suggested test scope; feeds an `impact` dimension alongside `postMergeRisk`
- **Review ordering** — blast radius reused in the PR review (v3.5.0): files ranked by impact, "start with these 2 files"
- **Feedback loop** — rejected impact predictions / auto-resolutions lower the pattern's confidence (extends `useResolutionMemory`), the local analog of Greptile v4's false-positive reduction; the Engine Accuracy release's lot F (derive the repo's conventions by replaying its own history) is the active, measured form of the same idea — the two should share one store
- **Agents too** — exposed via `@gitwand/mcp` (`gitwand_impact`, `detect_silent_conflict`) and CLI only, never the `/agent` WebMCP page, which by design never touches a real repository or its history. Positioning: Greptile sells this as a paid API ("Genius API", $0.45/req) — ours is local, free, open source
- **Package-graph pre-filter (optional)** — when the repo already has an Nx, Turborepo or Bazel project graph, use it as a coarse first pass: if `main`'s changed package isn't a dependency of the PR's changed package, declare a pass without loading tree-sitter at all. Falls back to the `pnpm-workspace.yaml`/`package.json` workspace graph GitWand already reads when none of the three is present, so this works the same on GitWand's own repo (plain pnpm workspaces, no Nx/Turborepo/Bazel) as anywhere else. Package-level only — two files inside the *same* package still go through the full reverse-dependency graph, since that's where `renamed_export_vs_import` actually lives
- **CI/CD gate** — `detect_silent_conflict` doubles as a CLI check (`gitwand check-semantic`, `packages/cli`), runnable as a GitHub Actions / GitLab CI job against a PR's would-be merge (fetch base + head, no working-tree side effects). Ships advisory first — inline PR annotations — following the `gitwand scan` precedent (v3.5.0: non-blocking badge, opt-in pre-commit hook before anything blocked); becomes a hard-blocking gate only once its false-positive rate is measured and cleared, the same discipline that kept `--regenerate` CLI-only at 38.5% agreement against an 80% bar (Engine Accuracy, v3.9.0). `benchmark-gate.yml` is the existing precedent for a hard block already living in this repo's own CI
- **Opt-in & lazy** — computed post-preview, never blocking the merge flow; enabled in Settings

- **Verification Plans attached to handoffs** (Snipara) — every PR/change carries the checks it must pass; overlaps with the CI annotations (v2.18.0).

### Measured and declined, known properties

- **libgit2 phase 2: stage/unstage** (moved out of v3.11.0, 2026-09-14, **measured and declined**): the plan was index-level `git2` staging behind a CLI fallback, mirroring the v3.10 `git_diff` migration. Measured before building, and the numbers say not to. **Perf:** the win is a flat ~15 ms, which is the subprocess spawn and nothing else, because both paths pay the same hashing cost. `git add` against libgit2, median of 7 runs: 1 file 17.1 vs 1.8 ms, 100 files 79.7 vs 64.1, 1000 files 926.7 vs 874.7, 5000 files 4997 vs 4487. Staging is batched (one call for N paths), so that 15 ms is per user action, and every `stageFiles` is followed by a `refresh()` whose `git status` alone costs 20 ms on a 1000-file repo and 31 ms on 5000. The saving is smaller than the refresh that immediately follows it. **Correctness:** 8 of 9 scenarios write a byte-identical index (modified, untracked, deleted, CRLF under `text=auto` + `core.autocrlf`, exec bit, symlink, conflicted-resolve, and `unstage` via `reset_default`). The ninth diverges: libgit2 implements the built-in CRLF filter but **executes no external `filter.<name>.clean` process**, which is exactly the Git LFS mechanism. A probe with a filter rewriting `SECRET` to `REDACTED` had the CLI store `value=REDACTED` and libgit2 store `value=SECRET`; on an LFS repo that is the raw binary in the index instead of the pointer, and git then reports the file as `AM` rather than `A`, so it reads as "still modified" rather than as corruption. A guard is possible (`repo.get_attr(path, "filter")` to detect filtered paths and defer to the CLI), but a fast path plus a detector plus a fallback plus parity coverage, all for 15 ms, does not pay for itself. Revisit only if staging latency becomes a real complaint, in which case the measurement points at the post-action `refresh()` rather than at `git add`, and the v3.10 watcher is already the infrastructure for that.
- **libgit2 blame** (moved out of v3.11.0, 2026-09-14, because it cannot be completed on demand): `git_blame`'s fast path was written, tested and then left disabled in v3.10.0. `blame_attribution_matches_the_cli_on_a_moved_block` exposed a git-version-dependent attribution divergence on a moved block between libgit2's bundled Myers xdiff and the CLI's histogram blame: green against git 2.50.1, red against 2.55.0. This is a disagreement between two algorithms, not an unfinished task, so it has no estimate and no owner action short of resolving the divergence upstream or reimplementing the attribution. Blame attribution is user-visible, so the CLI stays authoritative. `libgit2_blame` and its tests stay in tree as the regression guard; re-enabling it means resolving the divergence first, not deleting the test.
- **Snapshot refs are visible to a bare `git log --all`** — GitWand excludes them from every traversal it runs, but any ref under `refs/` is by definition part of `--all`, so a user typing it in a terminal sees snapshot commits, exactly as they see `refs/stash`. Nothing to fix short of abandoning refs entirely (which would let `gc` eat the snapshots); documented here so it is a known property rather than a surprise.
- Claude Code still creates one empty `~/.claude/projects/<run-dir>/` folder per run (no flag avoids it; `--no-session-persistence` already drops the transcript)

## Vision

GitWand is a native Git client that **understands** code, resolves trivial conflicts on its own, and makes visible what the terminal hides.

Positioning: neither "yet another Git GUI" nor an IDE. A first-class Git navigation tool — fast, local-first, cross-platform — with a unique algorithmic intelligence for conflict resolution, and a surface for interacting with AI agents (MCP, Agent Sessions, terminal).

**Core values**: open source (MIT) · native performance (Tauri 2 + Rust) · zero mandatory cloud · every feature optional and explicit.

## Design principles

1. **Intelligence first** — Every screen should offer more than the terminal.
2. **Native performance** — Tauri 2 + Rust. Sub-1s startup, smooth on 100k+ commits.
3. **Progressive** — Works immediately for simple cases. Advanced features are discovered naturally.
4. **Cross-platform** — macOS, Linux, Windows. Same quality everywhere.
5. **Free and open source** — Core and desktop under MIT.
6. **Refusal is structured, not silent**: any tool that declines to decide (a pending hunk, a detected silent conflict) hands back `agent_guardrails` built only from facts it actually computed (the diff, the signature, the missing argument), never inferred domain judgment like "this is security-critical." Applies everywhere a `@gitwand/mcp` tool can refuse (`gitwand_resolve_conflicts` today, `detect_silent_conflict` in v4.3.0); the `/agent` WebMCP page has no repository to reason from, so it never carries this.
